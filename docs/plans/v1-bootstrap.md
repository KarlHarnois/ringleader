# Plan: Ringleader, a tmux session manager for Claude and opencode

> Status: active. The milestone 30 commit flips this to `completed`. This file is the historical plan, not living documentation; `AGENTS.md` is the living documentation.

## 0. Ground rules for the implementing agent

- Load the clean-code skill before writing any code.
- Comments are treated as failures to express intent in code. Every comment is a signal, not documentation: revisit the code it explains and improve it until the comment is unnecessary, then delete the comment. Rename the variable, extract the function, introduce the type, or restructure the control flow that made the explanation feel needed. Never add a comment to justify messy code, and never leave a comment as a substitute for a better name. The only surviving comments are the clean-code exceptions: legal headers, non-obvious intent that cannot be encoded in structure, warnings of real consequences, and TODOs that reference a tracked issue. A surviving comment is never announced in a commit body. Instead, the implementing agent stops and justifies the comment to the project owner before committing. If the justification against an exception is not convincing, delete the comment and fix the code instead. This rule outranks convenience; a commit that adds an unjustified comment is not done.
- Write object-oriented Rust: state in structs with private fields, behavior in `impl` blocks, traits as interfaces, composition over inheritance, dependencies injected through constructors. No free functions except `main` and `#[test]` functions, which Rust requires to be free. A test helper that is not a `#[test]` function is a method or associated function of a fixture struct. A fixture struct used by one file's tests lives in that file's `mod tests`, and one shared across files lives in `src/test_support/` with a tree entry. `main.rs` holds `fn main` and `CompositionRoot`, whose methods build the adapters and services. Argument parsing and dispatch stay in `Cli`.
- One primary type per file, file named after it in snake case. The tree in section 3 is the file contract: every listed file exists and holds its one type. Types absent from the tree are support types (error enums, builders, request structs, iterators, parser results, dialog state) and fold into their owner's file. Unit tests live inline in `#[cfg(test)] mod tests`. `mod.rs` declares and re-exports only. Source files target under 200 lines excluding tests.
- Commit after every milestone item. Capital first letter, title under 72 chars, imperative body.
- Build, test, and run every tool inside `nix develop`. The host PATH may carry other versions of `cargo`, `rustc`, and `tmux`, including a tmux newer than the pinned one, so never rely on what the host provides.
- Stage each new file by path with `git add` before running any `nix` command, because `nix develop`, `nix build`, and `nix flake check` ignore files outside the git index.
- Every ad-hoc tmux command, such as a binding experiment, runs as `env -u TMUX -u TMUX_PANE tmux -u -S <tempdir>/x.sock -f /dev/null ...` and ends with `kill-server` on that socket. `nix develop` passes `$TMUX` through, so a bare `tmux` command reaches the user's live server. Never touch the default server or the server named in `$TMUX`. Keep the socket path under 100 bytes, because tmux rejects a longer one with `File name too long`. Use a directory from `mktemp -d` under `/tmp`, or `cd` into the scratch directory and pass a relative path such as `-S ./x.sock`.
- Every manual run of the `ringleader` binary, TUI or CLI, uses throwaway state, because production `TmuxCommand` passes no socket or config arguments and `main` resolves the real XDG paths. Create `<tempdir>` with `mktemp -d /tmp/rl.XXXXXX`, and inside it `tmux-<uid>` with mode 0700 (`<uid>` from `id -u`), `config/ringleader`, `state`, `data`, `run`, and `repos`. The prefix is `env -u TMUX -u TMUX_PANE -u RINGLEADER_CONFIG TMUX_TMPDIR=<tempdir> XDG_CONFIG_HOME=<tempdir>/config XDG_STATE_HOME=<tempdir>/state XDG_DATA_HOME=<tempdir>/data XDG_RUNTIME_DIR=<tempdir>/run`, which sends Ringleader's tmux calls to the private server at `<tempdir>/tmux-<uid>/default`. Every tmux command typed for that server uses the prefix and also passes that path with `-S`, because tmux silently uses the user's default server when `TMUX_TMPDIR` names a missing directory. Before the binary runs, start the server with the prefix and `tmux -u -S <tempdir>/tmux-<uid>/default -f /dev/null new-session -d -s holder`, so it never loads the user's tmux config. Before the first run, write `<tempdir>/config/ringleader/config.toml` with one stand-in agent, `name = "stand-in"` and `command = "sh"`, and never `claude` or `opencode`. Build fixture repos under `<tempdir>/repos` with the hermetic git environment of section 10, and run the binary by absolute path with `<tempdir>/repos` as the working directory, so no real repository is in scope. An outside-tmux check runs the binary with the prefix in a pane of a second server started under the ad-hoc tmux rule. An inside-tmux check runs it in a pane of the `holder` server with the prefix minus `-u TMUX -u TMUX_PANE`. End with `kill-server` on each socket by explicit `-S` path, then remove `<tempdir>`. Never run the binary against the user's tmux server, config, state, data, or repositories.
- The private GitHub repository exists and is configured as `origin`. Do not create another repository or add another remote. Push only when the project owner asks.
- Keep the repo consumer-agnostic. Never reference or assume any specific downstream setup, local directory layout, or personal configuration. Examples and fixtures use generic names such as `example-project`.
- Human-facing prose uses "Ringleader". Identifiers stay lowercase: binary, crate, repo, flake input, config paths, tmux and branch prefixes, JSON fields.
- While the header says `active`, this file is the source of truth for v1. If something here conflicts with an instruction received later, stop and ask. Once the header says `completed`, `AGENTS.md` and newer plans under `docs/plans/` take precedence over this file.

## 2. Locked decisions

- Rust, single binary crate, synchronous event loop with polled input, no async runtime. Helper threads from `std::thread` are allowed, such as the readers of a child's pipes (section 9) or the repo scan worker (section 5), which keeps slow work off the event loop.
- `ratatui` + `crossterm`.
- Hexagonal architecture: `ui` and `adapters` depend on `application`, `application` depends on `domain`, `domain` depends on nothing. `main.rs` is the only composition root.
- Object-oriented design throughout, in Rust terms: state lives in structs with private fields, behavior in `impl` blocks, traits define the ports (interfaces), composition over inheritance. Constructors (`new`) and dependency injection through function arguments. No free functions except `main` and `#[test]` functions. No `pub` data fields, access is through methods. This applies to domain, application, adapters, and UI equally.
- One primary type per file, named after it in snake case. The tree in section 3 is the file contract, and every listed file holds its type. Types not in the tree are support types that fold into their owner's file. Unit tests live inline in `#[cfg(test)] mod tests`. `mod.rs` files declare and re-export only. Source files target under 200 lines excluding tests; when one outgrows that, extract its largest behavior-bearing type into its own file and update the tree in section 3, or the tree in `AGENTS.md` from milestone 29 on.
- Repo discovery is contextual. The picker scans from the directory the app was launched from. Inside a git repo, the scope is that repo plus a bounded walk of the launch directory, whether the launch directory is the repo's top level or below it. The walk's repos merge with the enclosing one. Outside a repo, the scope is a bounded walk of the launch directory. Explicit `[[repos]]` entries remain as overrides for custom names, custom `base_branch`, and repos that must always be visible. Explicit entries win on path collision. A repo's identity is its canonical path, and its name is a display label that two repos can share.
- The session list is never filtered by scan scope. Existing sessions always show regardless of cwd.
- The scan walk is bounded by `scan_depth` (default 3). It goes breadth first and reads each directory's entries sorted by name, so when the 5,000-directory cap stops it, every repo at a smaller depth has already been found. Below the scope root it never descends into a directory whose name starts with `.`, or into `node_modules`, `target`, `vendor`, or `dist`, so tool and plugin clones under hidden directories stay out of the picker. Below the scope root, a `.git` directory marks a repo and stops descent. A `.git` file gets the "Add repo" `git rev-parse` check (section 6): a linked worktree or a submodule is skipped, and a repository created with `--separate-git-dir` is listed. Symlinks are not followed, and network and FUSE mount points below the scope root are never entered (section 8). A directory whose listing or `.git` check fails is skipped, whatever the error, and only a scope root that cannot be listed fails the scan. Worktrees and submodules never appear as repos.
- Delete removes the worktree and deletes the branch. It warns and double-confirms when the worktree is dirty, when the branch, the worktree HEAD, or one of the worktree's submodules has commits that exist on no other ref, or when a process outside the tmux session runs in the worktree. It requires explicit confirmation while the agent is `Working`. Before it removes anything, it stops the session's processes and refuses when one survives or when a commit landed after the guards counted.
- Worktree removal uses `git worktree remove --force` only. There is no recursive-delete fallback, and Ringleader never deletes worktree files itself. git's removal is not atomic. When it cannot delete an entry, such as a read-only directory or a directory another user owns, it does not restore what it already deleted, unregisters the worktree anyway, and exits nonzero. The deleted entries can include the `.git` file. `delete_session` step 6 reports that leftover.
- Rename renames the tmux session, the registry entry, and the git branch by default. `--keep-branch` and a dialog toggle opt out. The worktree directory name does not change.
- Ringleader's own styles, defined in `Theme`, use ANSI named colors and modifiers only. Base style `Color::Reset`. Selection `Modifier::REVERSED`. Diff green/red. `Theme` never uses RGB or indexed colors. The preview is the exception. It shows the agent's captured colors as `ansi-to-tui` parses them, including `Color::Indexed` and `Color::Rgb`, with no conversion to named colors.
- Worktrees live under `$XDG_DATA_HOME/ringleader/worktrees/<repo>/<slug>`, outside the repos.
- The app owns its config file. No config file is managed by Nix.
- MSRV 1.95, edition 2024, matching the rustc shipped in nixpkgs 26.05 (rustc 1.95.0, verified). Milestone 1 confirms this against the dev shell before any code is written.
- Session state is observed from tmux, not inferred from agent internals. A pure classifier turns observations into states. Activity comes from `window_activity` of the agent window, an epoch-seconds format variable that updates within 1 second of pane output. It covers every pane in the agent window, so output in a pane the user splits off the agent window also counts as agent activity and can hold the session in `Working`. tmux 3.6a has no per-pane activity time, and `pane_last_output_time` is not available.
- The agent pane is tagged with the pane user option `@ringleader_agent 1` (`set-option -p`) at creation. It is a pane option rather than a window option, so a pane the user splits off the agent window never carries the tag. Observation, preview capture, attach, and respawn use only the tagged pane, addressed by its `pane_id`. Activity and the attached-client count are the exceptions, since tmux tracks both per window. Other panes and windows in a managed session, including the `t` shell window and windows the user opens, are ignored.
- User `after-` hooks, such as `after-new-session`, `after-new-window`, `after-set-option`, `after-rename-session`, and `after-display-message`, run inside the invocation that triggered them. They can print to its stdout before or after Ringleader's lines, split the new window, rename or kill the new session, and fail. A failing hook makes tmux exit nonzero although every later Ringleader command still runs. Query commands run their `after-` hooks too, such as `after-list-panes`, `after-list-clients`, `after-list-keys`, and `after-capture-pane`. Every `-F` format and every `display-message -p` format that Ringleader passes therefore starts with a fixed label, and `TmuxCommand` reads values by label and ignores every other line. A query, such as the `list-panes` call of `observe_all`, a pane check, or the `#{pid}` check of `repair_stale`, reads its values from its labeled lines whatever the exit status. `capture-pane` output carries no label, so lines that an `after-capture-pane` hook prints show at the bottom of the preview. A capture fails only when tmux exits nonzero with empty stdout. `new-session` passes `-P -F 'ringleader-created #{session_id} #{pane_id}'`, and every `new-window` passes `-P -F 'ringleader-created #{window_id} #{pane_id}'`. Every invocation that changes tmux state ends with a `display-message -p` whose output starts with `ringleader-done`, and that line, not the exit status, decides success. The outside-mode `attach-session` child is the exception, because a `display-message -p` after it prints into a view-mode overlay on the attached pane instead of stdout. When the `ringleader-done` line is present and tmux exited nonzero, Ringleader logs the unlabeled lines and stderr as a warning and continues, since tmux prints a failing `run-shell` hook's message on stdout. When that line is absent, a Ringleader command failed and stopped the sequence, and the adapter kills, by its printed id, what the invocation created, with `kill-session -t '$<n>'` or `kill-window -t @<n>`. The id still names a session that a hook renamed. That kill ignores `can't find session`, `can't find window`, `no server running on <path>`, `error connecting to <path> (No such file or directory)`, and `server exited unexpectedly`. When tmux exits without a `ringleader-created` line, nothing was created, such as on `duplicate session`, so nothing is killed. A timed-out invocation is handled by section 5 step 5 instead, because it can still create the session. A hook that splits the new window makes `=<session>:` name the hook's pane, so the agent tag would land on the wrong pane. The `ringleader-done` line after `new-session` or the agent `new-window` therefore carries the `pane_id` of `=<session>:`. When it differs from the created pane, a second invocation unsets `@ringleader_agent` and `remain-on-exit` on that pane and sets both on the created `pane_id`. It ends the same way, and when it fails, the adapter kills what the first invocation created, by the same id. `destroy-unattached off` is already set by then, so the second invocation cannot destroy the session. Window options such as `@ringleader_shell` are unaffected, since the split stays in the new window. Notification hooks such as `session-created` run after the invocation and do not affect the tag.
- Every tmux target that Ringleader builds is exact: `=<session>:` for sessions, a `window_id` such as `@4` for windows, and a `pane_id` such as `%3` for panes. The rollback above also uses a `session_id` such as `$2`. Used as a window or pane target, `=<session>:` means the session's current window or pane, so it addresses a particular one only inside the invocation that just created it. A bare `-t <name>` prefix-matches other sessions on tmux 3.6a (`kill-session -t ringleader-fix` kills `ringleader-fix-auth`), so it is never used. Milestone 6 confirms the exact form per command on the pinned tmux.
- Quitting with `q` exits the TUI only. Managed tmux sessions keep running in the background and are rediscovered on the next launch.
- Session metadata is mirrored into tmux session user options so a live managed session can be adopted back after a restart or registry loss.
- Managed tmux sessions are created and configured in a single tmux invocation (`new-session ... ; set-option ...`). Setting options in a second call can destroy the session when the user's global `destroy-unattached` is on. The command separator is a standalone `;` argv element, never a shell-escaped `\;` from Rust. tmux treats any argv element ending in `;` as a separator, so every other dynamic argument in a tmux invocation (paths, names, option values) that ends in `;` is escaped by inserting a backslash before the final `;`.
- `TmuxCommand` passes `-u` on every tmux invocation. Without it, a client whose locale is not UTF-8, such as one in the Nix build sandbox with no `LANG`, gets every tab and every non-ASCII byte of command output replaced with `_`. That breaks the tab-separated `list-panes` rows, the metadata JSON, and saved key bindings.
- Every tmux child process that Ringleader spawns gets exactly the injected `ProcessEnvironment` snapshot with the configured agent `env` names removed. A new tmux server copies its first client's whole environment into its global environment, so without the removal a server that Ringleader starts would hand the agents' secrets to every pane on it, including `t` shells and the user's own windows. `TmuxCommand` passes `-N` on every invocation except one that runs `new-session`, because `attach-session`, `list-keys`, `list-commands`, and `start-server` would otherwise start a stray server under the user's tmux config, and only `new-session` receives the current union of names through `SessionSpec`. With `-N` those calls fail with `no server running on <path>` or `error connecting to <path> (No such file or directory)`, which callers treat as no server.
- Every `new-session` and `new-window` that Ringleader issues passes `-c <worktree path>`. Without it, tmux starts the pane in the calling process's directory. For a missing `-c` directory, tmux silently uses `$HOME` and still exits 0, so tmux success never proves the worktree exists. tmux expands formats in the `-c` value, so `TmuxCommand` doubles every run of `#` in the path that is not followed by `[`. Without the doubling, a path containing `#{` starts the pane in another directory and still exits 0, and a path containing `#(` runs a shell command. A run followed by `[` stays as written, because tmux copies such a run and its `[` verbatim, and doubling it would start the pane in `$HOME`.
- Managed tmux sessions set `destroy-unattached off`, so detaching, including via Ctrl-Q, never destroys them, even if the user's global config enables it. The server option `exit-unattached` instead ends the server, with every session on it, once no client is attached, and no session option overrides it. The creation's `ringleader-done` line therefore carries `#{exit-unattached}`. On `1`, creation rolls back as for any other failure and fails with a message naming the option.
- Managed tmux sessions set `remain-on-exit on` on the agent pane (`set-option -p -t =<session>: remain-on-exit on`), so an agent exit leaves a dead pane that `restart` can revive. The window form would also keep every pane the user splits off the agent window open as a dead pane after it exits. The pane setting survives `respawn-pane`. `remain-on-exit` is a window and pane option, not a session option.
- Detached sessions get an explicit size (`-x 200 -y 50` by default, configurable) so previews are not limited to 80x24. The size holds only until a client first attaches. tmux's default `window-size latest` then keeps the last client's size after it detaches, so the preview crops whatever size the pane has.
- Agents launch through a hidden `ringleader __exec-agent --handoff <path>` subcommand. Environment values and the agent argv never appear on a tmux command line. The creating process writes a handoff file holding the agent argv, the environment values, and the worktree path, and tmux runs only the launcher with the file's path. The launcher reads the file, deletes it, runs `env_clear`, sets exactly the environment from the file, sets the agent's directory to the worktree path with `Command::current_dir`, and execs the agent. A missing worktree path makes the launcher print an error and exit nonzero, so the dead pane shows the failure instead of an agent running in another directory. That environment is a fixed baseline (section 8) plus the agent's configured `env` names, with values taken from the creating process only. The launcher also keeps `TERM`, `COLORTERM`, `TMUX`, and `TMUX_PANE` from its own pane environment, read from the `ProcessEnvironment` snapshot that `main` captures, and sets `GPG_TTY` to the snapshot's terminal name, or leaves it unset when there is none. A name the creating process lacks is absent for the agent even if the tmux server's environment has it, so server environment drift never reaches the agent. The launcher never reads `config.toml`. Only variable names are configured and logged, never values.
- `main` captures the process environment once, with `std::env::vars_os`, together with the terminal name of standard input, into a `ProcessEnvironment` snapshot and injects it into `TmuxCommand`, `AgentLauncher`, `TomlConfigSource`, and `SystemHostProbe`, which resolves agent commands on the snapshot's `PATH`. `main` also passes the snapshot's `$SHELL`, with `sh` as fallback, to `SessionAccess`, which uses it for the shell window and the ephemeral shell request. `main` passes the snapshot's `HOME` to `RepoCatalog` for typed paths (section 8). `main` passes `TmuxCommand` the union of every configured agent's `env` names at startup, and `SessionSpec` carries that union from the current config, so a name added by `r` is still removed from the `new-session` call that can start a server. Nothing below `main` reads the process environment. Tests pass fixture snapshots, read only their own `PATH` (section 10), and never call `std::env::set_var`, which is `unsafe` in edition 2024 and racy across test threads. `vars_os` also never panics on a non-UTF-8 variable, which `std::env::vars` does. `main` reads `RINGLEADER_TMUX` and `RINGLEADER_GIT` from the snapshot, removes both from it so no tmux server inherits them, and passes them as program paths to `TmuxCommand` and to every adapter that runs git. When one is unset, the program is `tmux` or `git` found on the snapshot's `PATH`, which is what tests and `nix develop` use (section 12).
- Base branch resolution never fetches. It reads local refs only. On a repo with an unborn HEAD, no `base_branch` set, and nothing on the ladder resolving, creation runs `git worktree add --orphan -b <branch> <path>`, which needs git 2.42 or newer. Branches are always created with `--no-track`, so an agent branch never gets an upstream. The orphan form is the one exception: git rejects `--no-track` with `--orphan`, and an unborn branch has no upstream to set.
- Session names use one canonical slug function for the registry name, tmux session name, worktree directory, and branch, with a 64-character cap and uniqueness checked on the slug. The slug alphabet (section 4) makes every slug a legal tmux name and a legal git ref component by construction, so the domain validates without calling git.
- Attach behavior and bell delivery depend on an inside-tmux flag that `main` computes once with `TmuxCommand::is_inside_client` and injects into the tmux adapters and the `App`. The flag is true when `$TMUX` and `$TMUX_PANE` are set, `display-message -p -t <TMUX_PANE> 'ringleader-pane #{pane_id} #{pane_pid} #{pane_tty}'` confirms the pane, and the pane shows this process: this process, or an ancestor between it and `#{pane_pid}`, has `#{pane_tty}` as its controlling terminal and is in that terminal's foreground process group. The ancestor case covers an editor terminal inside the pane, such as Neovim `:terminal`. An ancestor, the pane process included, counts only when its child in the chain does not have `#{pane_tty}` as its controlling terminal. In Neovim that child is the server process, which has no controlling terminal. A shell idle at its prompt, nested or not, is the foreground of its own pane, but a terminal emulator started from it as a background job keeps `#{pane_tty}` as its controlling terminal, so that shell does not count. A terminal emulator or IDE started from a pane inherits both variables but is not in the pane's foreground, so it gets outside mode. `attach-session` works there because tmux reports nesting only when the attaching client's own terminal is a pane. A terminal emulator started in the foreground of a pane still reads as inside, and `env -u TMUX -u TMUX_PANE ringleader` forces outside mode against the default server. The flag is also true when `$TMUX` is set and `$TMUX_PANE` is not, as in a `display-popup`, and then the TUI installs no return binding (section 6). `main` reads the parent chain once into `CallerProcess`, a support type of `TmuxCommand` that holds the process group, controlling terminal (`tty_nr`), and terminal foreground group (`tpgid`) from `/proc/<pid>/stat` for this process and each ancestor, so tests inject fixture chains. Outside mode runs `tmux attach-session` as a child under the terminal guard. Inside mode runs `tmux switch-client`, which switches the current client, and the TUI keeps running. A child process whose terminal is a pane cannot use `attach-session`; it fails with "sessions should be nested with care".
- Only the TUI installs the Ctrl-Q return binding. The CLI never touches tmux key bindings.
- Locks are taken once per process by the entry point, never inside `application`. `main` takes the TUI's lifetime lock before building the `App`, and `Cli` takes the write lock for mutating commands.
- Mouse support is out of scope for v1.
- Terminal bell on `Working` to `Waiting` is config-gated, off by default. Outside tmux, the TUI writes BEL to its own terminal while the home screen shows. It does not poll during an attach, so no bell fires then. Inside tmux, BEL goes to the tty of every client on the server except control-mode clients, so it reaches the user in any session, even when the TUI's pane is hidden. A session whose agent window a client shows never rings, since the user is already looking at it.
- No short alias next to `ringleader` unless asked later.
- MIT license, matching the project owner's other personal tools. `LICENSE` holds the standard MIT text under the heading `The MIT License (MIT)`, with the line `Copyright (c) Karl Rivest Harnois` and no year. `Cargo.toml` sets `license = "MIT"`.
- v1 supports Linux only, on `x86_64-linux` and `aarch64-linux`. Adapters may read `/proc`. macOS and other platforms are out of scope.

Rules for `AGENTS.md`:

- `domain` never imports `crossterm`, `ratatui`, `std::process`, or any adapter.
- `application` defines traits and use cases, never shells out, never touches the filesystem directly, and never reads the system clock.
- `ui` calls the `SessionService` facade only. `SessionLifecycle`, `SessionMonitor`, `SessionAccess`, `RepoCatalog`, and `Doctor` are composed by the facade and are not called from `ui` or `cli.rs`.
- OOP in Rust: all state in structs with private fields, all behavior in `impl` blocks, traits as interfaces, composition over inheritance, one primary type per responsibility, dependencies injected through constructors. No public data fields, no free functions except `main` and `#[test]` functions. A test helper that is not a `#[test]` function is a method or associated function of a fixture struct.
- One primary type per file, named after it in snake case. Supporting types owned by the primary type live in the same file. Unit tests live inline. `mod.rs` declares and re-exports only. The tree in section 3 is the file contract; do not merge primary types into one file. Source files target under 200 lines excluding tests. When one outgrows that, extract its largest behavior-bearing type into its own file. A commit that adds a file under `src/` that the tree does not list, or moves, renames, or removes a listed file, updates the tree in section 3 in the same commit.
- `cli.rs` owns the clap argument structs (`ListArgs`, `NewArgs`, and so on) as support types of `Cli`. They get no files of their own.
- Why the tree splits what it splits: `Session`, `SessionName`, and `SessionState` each get a file because each is used independently across modules, carries behavior or invariants, and changes for its own reasons. Merging files later is mechanical; splitting a file that grew is disruptive, so prefer the separate file. The reverse is also true: do not invent files for types the tree does not list.
- `src/test_support/` is `#[cfg(test)]` only and must not appear in the binary. It exists so unit tests across modules share one set of hand-written doubles and fixtures.
- Other support types, such as a parser result, a doctor finding, a session spec, or a dialog's in-progress state, live in their primary type's file and get no tree entry.
- No code below `main` calls `std::env::current_exe`, reads the process environment (including `$TMUX`, `$TMUX_PANE`, `$HOME`, and `$SHELL`) or the process cwd, resolves XDG paths, or asks which terminal standard input is. `main` reads them once and injects them, with environment values in the `ProcessEnvironment` snapshot. The snapshot also holds the terminal name of standard input, or none when standard input is not a terminal. `ProcessEnvironment::capture`, the constructor `main` calls, reads it with `libc::ttyname_r` on descriptor 0, in the type's only `unsafe` block.
- Comments: the repository is comment-hostile. Every comment is presumed unnecessary until proven otherwise. The fix for "this needs explaining" is better code: rename, extract, type, restructure. When a comment seems to survive, stop and justify it to the project owner before committing; never announce comments in the commit body. Doc-comments are comments and follow the same rule; do not document what a well-named item already says.
- Human-facing prose uses "Ringleader". Identifiers stay lowercase.
- Do not create another repository or remote. Push only when the project owner asks.

## 4. Domain

- `SessionName`: one canonical slug function used for registry name, tmux session name, worktree directory, and branch. The slug lowercases the input, maps every character outside `[a-z0-9-]` to `-`, collapses runs of `-`, trims `-` at both ends, truncates to 64 characters, and trims again. An empty result is a validation error (exit 1). The alphabet makes every slug a legal tmux session name (no `:` or `.`) and a legal git ref component, so `SessionName` validates in pure Rust and never calls git. Uniqueness is global across repos and checked on the slug, so two names that slug to the same string are rejected. Availability beyond the registry (worktree directory and branch) is checked by `SessionLifecycle` through the ports.
- `RepoName`: the same alphabet and slug function as `SessionName`. Names derived from a directory basename are slugged. A repo name is a path segment under `worktree_root`, so the alphabet also rules out `/` and `..`. A name is a display label, not an identity. Two repos at different canonical paths can share one, and their worktrees then share `<worktree_root>/<repo>/`, which is safe because session slugs are unique across repos.
- `Agent`: name, `command`, `args`, environment variable names the launcher restores, and `prompt_args`, the argument template used to pass an initial prompt. The name is the lookup key used by `--agent`, the registry, and `@ringleader_meta`, compared exactly, and is also what the UI displays. Values are never stored in the domain.
- `SessionState`: `Working`, `Waiting`, `Exited`, `Stopped`, `Unmanaged`. `SessionState` owns the bell edge predicate: it is true only for a previous `Working` followed by a current `Waiting`.
- `Session`: name, repo name, repo path, worktree path, branch, base commit, agent, tmux session name, tmux socket path, created timestamp (epoch seconds), and the canonical `worktree_root`, `branch_prefix`, and `tmux_prefix` in force when it was created or adopted (section 8). The base commit is the start-point SHA resolved at creation, empty for an orphan worktree. The socket path is the server's `#{socket_path}`, read in the creating invocation. With thirteen fields, `Session` is built through a builder or a parameter struct, since a thirteen-argument `new` fails `clippy::too_many_arguments` under `-D warnings`.
- `SessionMetadata { repo_name, repo_path, branch, base_commit, worktree_path, agent }`, the copy mirrored into tmux.
- `SessionObservation { exists, attached, pane_dead, activity_at, created_at, socket_path, metadata: Option<SessionMetadata> }`, built from the tagged agent pane only. `attached` is true when any client shows the agent window, read from `#{window_active_clients}`. A client on the `t` shell window of the same session does not count. `socket_path` is the server's `#{socket_path}`. A live session with metadata but no tagged agent pane is observed with `pane_dead` true.
- `Config`: parsed `config.toml`, with explicit repo overrides, agents, prefixes, refresh intervals, and the bell flag. Its constructor runs the load checks of section 8 and returns every failure, not only the first.
- `RepoScope`: the enclosing repo, if any, and the scope root where the bounded walk starts, produced by `RepoScanner`. It also records when the walk-up ended at a `.git` file that names no enclosing repo, such as a linked worktree whose main repository git cannot name or a `.git` file whose check fails. Support type on `Repo`. The launch directory enters through `main` and is threaded through the service, so neither domain nor application reads the process cwd.
- `SessionClassifier`, pure, takes `now` as an argument, never reads the clock itself. `now` and `activity_at` are `u64` epoch seconds. No stored history:
  1. session missing, `Stopped`
  2. no valid metadata (malformed, absent, or rejected by the adoption or pairing checks in section 8), `Unmanaged`
  3. `pane_dead`, `Exited`
  4. `now.saturating_sub(activity_at) < activity_idle_seconds`, `Working`, so an activity time later than `now` counts as fresh
  5. otherwise, `Waiting`
- `DiffStat { files, insertions, deletions, untracked }`, computed per request, not stored. It measures the worktree against the session's base commit: everything the agent committed plus uncommitted tracked changes. For an orphan worktree the base is the empty tree, obtained with `git -C <worktree> hash-object -t tree /dev/null` so SHA-256 repositories work too. Run outside the repository, the same command prints the SHA-1 empty tree. `untracked` counts files git would add but does not track yet. A binary file counts as one file with zero insertions and deletions. It is computed with `git diff-index --numstat <base>` and `git ls-files --others --exclude-standard -z`, both run with `GIT_OPTIONAL_LOCKS=0` and `-c core.fsmonitor=false` (section 5). Porcelain `git diff` refreshes and rewrites the worktree's index under `index.lock`, even with optional locks off, which makes the agent's own `git add` fail while a poll runs. `diff-index` writes nothing and never detects renames, so user config cannot change the totals.
- `SessionSummary { session, state, attached, diff: Option<DiffStat> }` is what the service returns to the UI. `attached` copies `SessionObservation.attached` and is false when the tmux session is not live. `App` reads it to suppress the bell. `diff` is `None` until computed and always `None` for `Unmanaged` sessions.

`Waiting` is the green bullet: the pane is running and quiet, so the agent is at its prompt. `Exited` requires `remain-on-exit on` on the agent pane, set at creation, so the pane survives agent exit and `respawn-pane` can restart it.

## 5. Ports and use cases

Ports:

- `SessionRegistry`: `load`, `save`.
- `Workspace`: `create_worktree(repo, path, branch, start_point)`, `remove_worktree`, `unlock_worktree(repo, path)`, `list_worktrees(repo)`, `list_worktree_dirs(root)`, `delete_branch`, `rename_branch`, `branch_exists`, `list_branches(repo, prefix)`, `resolve_start_point(repo, base_branch)`, `dirty_state`, `unmerged_commits(repo, branch, worktree)`, `diff_stat(worktree, base_commit)`, `validate_repo`, `version`. `resolve_start_point` returns either a commit SHA or the orphan case. `list_worktrees` entries carry the path, branch, HEAD, and the locked and prunable flags from `git worktree list --porcelain`. git prints every path with symlinks resolved, even for a missing worktree, so every comparison between a stored worktree path and a listed path first canonicalizes the stored path the way `delete_session` step 3 does.
- A branch is unborn when a `list_worktrees` entry names it but `git rev-parse --verify -q refs/heads/<branch>` fails, which is an orphan session's state before its first commit. A branch is missing when no entry names it and the same check fails. A delete retried after step 7 finds its branch missing. So does an orphan session's delete retried after step 6, because removing the worktree drops the only record of an unborn branch, and so does a branch the user deleted by hand. `branch_exists` is true for an unborn branch and false for a missing one.
- `unmerged_commits` counts commits reachable from the branch tip or from the worktree's HEAD that no other branch, tag, or remote-tracking ref reaches: `git rev-list --count <tip> <HEAD> --not --exclude=<branch without refs/heads/> --branches --tags --remotes`. It reads the tip and the HEAD once and returns both SHAs with the count, so the guard and the recovery record in `delete_session` describe the same commits. Including the worktree HEAD counts commits made on a detached HEAD. The HEAD comes from the `list_worktrees` entry, which still reports it when the worktree directory is missing. Each positive argument is left out when it does not resolve: the tip when the branch is unborn or missing, and the HEAD when the entry shows the all-zero HEAD of an unborn branch or no entry lists the worktree. With neither left, this part of the count is 0 without running git. The submodule walk below still runs. Never use `--all`. It includes the HEAD of every worktree, and every session's branch is checked out in its own worktree, so the count would always be 0. With `--branches`, the exclude pattern must drop the `refs/heads/` prefix, or it excludes nothing.
- `unmerged_commits` also counts the local commits of the worktree's submodule repositories. A linked worktree keeps them in the `modules` directory of the git dir that `git -C <worktree> rev-parse --absolute-git-dir` prints, and `git worktree remove --force` deletes them. The adapter walks that directory. A directory holding both `HEAD` and `objects` is a submodule git dir, and the walk descends from one only into its own `modules`, since a submodule name may contain `/` and submodules nest. For each, it adds `git --git-dir=<dir> --work-tree=<dir> rev-list --count HEAD --branches --not --remotes`, which also covers a submodule the agent deinitialized, since its git dir stays behind. `--work-tree` overrides the submodule's `core.worktree`, because git fails with `cannot chdir` once the agent deletes the submodule directory with `git rm` or `rm -rf`. When the worktree directory is missing, the git dir is instead the `worktrees/<id>` directory in the repository's common dir whose `gitdir` file, resolved against that directory when relative, names `<worktree>/.git`. The walk is skipped only when no such directory exists. While the worktree directory exists, the adapter also adds `git --git-dir=<worktree>/<path>/.git --work-tree=<worktree>/<path> rev-list --count HEAD --branches --not --remotes` for each `<path>` that `git -C <worktree> ls-files --stage -z` lists with mode `160000` and whose `.git` is a directory. Such a repository keeps its git dir inside the worktree, as when the agent commits a clone as a gitlink or `git submodule add` adopts an existing clone, and `git status` shows nothing once its gitlink is committed.
- `dirty_state` runs `git -c core.fsmonitor=false status --porcelain=v1 -z --untracked-files=all --no-renames --ignore-submodules=none` with `GIT_OPTIONAL_LOCKS=0`, so neither user config nor a `.gitmodules` `ignore` setting can hide new files, merge a rename into one entry, or hide a modified submodule. Every record then holds one path, and every file inside an untracked directory counts, except a directory with its own `.git`, which git prints as one record ending in `/`. `dirty_state` returns those nested repository paths with the count. It reports a missing worktree directory as `Missing`, never as an error. Ignored files are not counted, yet `git worktree remove` deletes them, so every delete warning says so.
- `GitWorkspace` and `DirectoryRepoScanner` remove the repository-local git variables from every git child, in production and in tests, after applying any environment override from the constructor: `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG`, `GIT_OBJECT_DIRECTORY`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_IMPLICIT_WORK_TREE`, `GIT_GRAFT_FILE`, `GIT_INDEX_FILE`, `GIT_NO_REPLACE_OBJECTS`, `GIT_REPLACE_REF_BASE`, `GIT_PREFIX`, `GIT_SHALLOW_FILE`, and `GIT_COMMON_DIR`. That is what `git rev-parse --local-env-vars` prints on git 2.54, minus `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT`, which git itself keeps when it enters another repository. A shell started by `yadm enter` or `vcsh enter` exports `GIT_DIR` and `GIT_WORK_TREE`, and git honors them over `-C`, so without the removal every call would act on that repository. Every git command that runs inside a worktree also sets `GIT_CEILING_DIRECTORIES` to the worktree's parent directory. In a worktree whose `.git` is missing, git then fails with `not a git repository` instead of answering for an ancestor repository, such as a dotfiles repo at `$HOME`. Every read inside a worktree, including `dirty_state` and `diff_stat`, passes `-c core.fsmonitor=false`, because `GIT_OPTIONAL_LOCKS=0` does not stop the repository's fsmonitor hook or daemon, and git waits for the hook on every call. The override makes git `lstat` every tracked file instead, a cost on large repositories that section 16 covers.
- `delete_branch(repo, branch, expected_tip)` runs `git update-ref -d refs/heads/<branch> <expected_tip>`, which git refuses when the branch no longer points at `expected_tip`. With no expected tip, as for an unborn or missing branch in `delete_session` step 7, it skips `update-ref`. Then, when `git config --local --get-regexp '^branch\.<branch>\.'` exits 0, it runs `git config --remove-section branch.<branch>`, because `update-ref` leaves the section that `git branch -D` removes, and a later session with the same slug would inherit its upstream. A missing section makes `--remove-section` exit 128 like any other fatal error, so the probe comes first. The `create_session` step 4 rollback passes the start point it resolved.
- `Multiplexer`: `create_session(spec)`, `kill_session`, `pane_pids(name)`, `has_session_on(socket, name, worktree_path)`, `caller_session`, `observe_all`, `attach(target)`, `capture_pane`, `rename_session(old, new, metadata)`, `respawn_agent`, `ensure_shell_window`, `ring_bell`, `server_version`, `server_exit_unattached`, `version`. `create_session` takes a `SessionSpec` support type (tmux session name, worktree path, size, metadata, agent argv, environment names, and the union of every configured agent's `env` names to remove from the tmux client) and is used both for new sessions and for recreating a `Stopped` session in its existing worktree. It returns the server's socket path. `create_session`, `respawn_agent`, and `ensure_shell_window` read their output by label and roll back their own invocations (section 2). `attach(target)` runs `attach-session` or `switch-client` based on the injected inside-tmux flag. Its target is an `AttachTarget` support type. `AttachTarget::Agent(session)` resolves to the tagged agent `pane_id`, which selects the agent window even after `t` made the shell window current. Only a session with no tagged agent pane is attached by `=<session>:`, and a lookup that fails refuses the attach rather than falling back to it. `AttachTarget::Shell(window_id)` takes the `window_id` that `ensure_shell_window` returns. `attach`, `capture_pane`, and `respawn_agent` resolve the tagged agent pane with a fresh `list-panes -s -t =<session>:` lookup rather than an id from an earlier poll. `rename_session` sends `rename-session -t =<old>: <new> ; set-option -t =<new>: @ringleader_meta <json>` in that order, then the `ringleader-done` line. The rename comes first, so when tmux refuses the new name, the session and its metadata stay unchanged, and the `set-option` targets the new exact name, because `=<old>:` no longer exists by the time it runs. `pane_pids(name)` runs `list-panes -s -t =<session>: -F 'ringleader-pane-pid #{pane_dead} #{pane_pid}'` and returns the process id of every live pane in the session, which `delete_session` uses as session ids. It skips dead panes, because tmux keeps reporting a dead pane's pid after the process exits, and Linux can give that number to an unrelated session leader. Processes that a dead pane left running in the worktree therefore count as outside processes. `caller_session` returns the session that holds the injected `TMUX_PANE`, or `None` when it is unset. It reads `TMUX_PANE` in outside mode too, since killing the pane a process was started from can hang that process up. `has_session_on` runs `list-panes -a -F` with a fixed label, `#{session_name}`, and `#{@ringleader_meta}` against a recorded socket with `-S`, and reports live when a session has that name or carries `@ringleader_meta` that names that worktree path. The zero-session errors of `observe_all` mean not live. Any other failure, such as `Permission denied`, refuses the action with an adapter error. `ring_bell` is the inside-tmux half of the bell (section 6). `server_version` reads the running server's `#{version}`, which can differ from the client's `tmux -V`. `server_exit_unattached` reads the running server's `#{exit-unattached}` for the `doctor` check of section 7.
- `ReturnBinding`: `install`, `restore`, `repair_stale`. See section 6, Attach and Ctrl-Q.
- `ConfigSource`: `load`, `add_repo`, `remove_repo`.
- `RepoScanner`: `resolve_scope(launch_directory) -> RepoScope` and `scan(scope)`, which returns the repos found, with canonical paths, and whether the visit cap cut the walk short. `scan` fails only when the scope root cannot be listed. The nearest-`.git` walk and the bounded directory walk both live in the adapter, keeping the service free of filesystem logic. `DirectoryRepoScanner` takes the visit cap and the mount table path through its constructor, so tests inject a small cap and a fixture table.
- `HostProbe`: `resolve_command(command)`, `is_writable(path)`, `path_exists(path)`, `is_file(path)`, `canonicalize_lenient(path)`. `delete_session` step 4 uses `path_exists` on the worktree directory and `is_file` on its `.git`, which is false both for a missing `.git` and for a `.git` directory. `canonicalize_lenient` canonicalizes the nearest existing ancestor of a path and appends the remaining components. It refuses a relative path, so nothing below `main` resolves one against the process cwd. `Doctor` and the use checks of `create_session` step 1 and `restart` (section 8) use the port. `resolve_command` looks up a `command` without `/` on the snapshot's `PATH` and checks that an absolute `command` names an executable file. `SessionLifecycle`, `SessionMonitor`, and `SessionAccess` also take the port, for the containment check that `delete_session` step 3 and reconciliation share and for every missing-worktree check that must run before tmux. `RepoCatalog` also takes it, to check typed paths (section 8) and to canonicalize configured repo paths in `discover_repos`. The port also has `processes_in(path, excluded_sessions)`, `session_processes(sessions)`, and `terminate(pids)`, which `delete_session` uses. `processes_in` lists, with pid and command, the processes whose working directory is the path or below it. It compares against the path canonicalized with `canonicalize_lenient`, because `/proc/<pid>/cwd` names the directory with symlinks resolved and a stored worktree path can contain a symlink. It skips members of the excluded sessions, Ringleader's own process, its ancestors, its child processes, and every process whose executable is named `tmux`, since a tmux server keeps the working directory of the client that started it and SIGTERM to it would end every session on that server. `session_processes` lists the processes whose session id is one of the given ids. `SystemHostProbe` reads `/proc/<pid>/cwd`, `exe`, `stat`, and `cmdline`, and skips a process it cannot read. It strips the `(deleted)` suffix that `exe` gains when an upgrade replaces a running binary, so a tmux server started before the upgrade is still named `tmux`. `terminate` sends SIGTERM and then SIGCONT to each pid with `libc::kill`, because a stopped process keeps SIGTERM pending until it continues. It polls every 50 ms for up to 5 seconds and returns the processes that remain. A process is gone when `/proc/<pid>` is absent or its state is `Z`. `terminate` is the only `SystemHostProbe` method with an `unsafe` block, which holds both `libc::kill` calls.
- `Lock`: `acquire_lifetime`, `acquire_for_write`. Used by `main` and `Cli` only.
- `Clock`: `now_epoch_seconds`. `main` injects `SystemClock`. `SessionMonitor` and `SessionLifecycle` take it and pass its value to `SessionClassifier`. `SessionLifecycle` also stamps a new session's created timestamp with it, and a `Stopped` session recreated in place keeps its original timestamp.

Application structure: `SessionService` is a thin facade that composes `SessionLifecycle`, `SessionMonitor`, `SessionAccess`, `RepoCatalog`, and `Doctor`, each with only the ports it needs. The use cases below are the facade's methods.

Use cases:

- `observe(persist)`: one `observe_all` call, reconcile, classify, no git. Returns summaries with no diffs. The TUI calls it on the `state_poll_ms` cadence with `persist` true, and the mutating session commands `new`, `delete`, `rename`, and `restart` call it with `persist` true under the write lock before they act, so a re-key or an adoption is written without a TUI (section 8). It writes the registry only when reconciliation changed something. `list` passes false, and so does a TUI that runs read-only on a failed config (section 8).
- `reconcile`: the step inside `observe` that merges the registry with live tmux sessions. Adopt live sessions matching `tmux_prefix` that carry valid metadata but have no registry entry. Keep registry entries with no live session as `Stopped`.
- `diff_stats(names)`: diffs for the given sessions only. The TUI passes one queued visible row per call (section 6), and `list` passes every session.
- `preview(name)`: capture the agent pane of one session, on the `preview_refresh_ms` cadence.
- `reload()`: reload config and registry from disk, used by `r`.
- `discover_repos(launch_directory)`: `RepoScanner.resolve_scope`, then `scan`, then merge explicit config overrides keyed by canonical path with explicit winning, dedupe, and return the repos sorted by name, then path, with the scan's cut-short and walk-up notices. Configured repo paths are canonicalized here, through `HostProbe::canonicalize_lenient`, never at config load. The call starts one `std::thread` worker and returns a `PendingRepos` support type at once, so a slow or stalled filesystem never blocks the event loop. `App` polls it every tick and drops it when the picker closes or the scope changes, and the CLI waits on it. While `new`, `repo add`, or `repo remove` waits on a worker, it checks its signal flags every 100 ms, and a raised flag makes it drop the write lock and end by that signal. `new` then never reaches `create_session`. This is the one exception to the rule of sections 7 and 9 that an interrupted use case finishes. Ending `repo add` or `repo remove` there never splits its use case, because its only change is one config rename (section 8). A blocked worker is abandoned, never joined. The worker holds `Arc` clones of `RepoScanner` and `HostProbe`, so both traits have `Send + Sync` as supertraits. Never filters sessions. The `n` dialog calls it when it opens and keeps the result until it closes, so every opening scans afresh. The launch directory is passed in from `main`, so the service never reads cwd itself. Changing the scope in the picker calls it again with the new path.
- `add_repo(path, name, base_branch)` and `remove_repo(name)` back the `n` dialog's "Add repo" row and the `repo` subcommands, and `repo list` prints `discover_repos`. `add_repo` validates the path with `validate_repo`, the "Add repo" check, and compares its canonical top level with the canonical path of every `[[repos]]` entry. Like `discover_repos`, it runs on a `std::thread` worker, because canonicalizing a configured path on a stalled mount blocks with no timeout. That worker holds `Arc` clones of `HostProbe`, `ConfigSource`, and `Workspace`, so `ConfigSource` and `Workspace` are `Send + Sync` too. The "Add repo" row polls it every tick while its busy message shows, and `repo add` waits on it as the CLI waits on `discover_repos`. When an entry's canonical path matches, `add_repo` writes nothing. It returns that entry, or refuses with a conflict naming the entry when the request gives a `name` or `base_branch` that differs from it. Before writing, it validates the edited document as config load does and refuses without writing when that fails, so a write never leaves a config that fails to load, such as one with a duplicate repo name. `remove_repo` finds the sessions that reference the entry by comparing its canonical path with each session's `repo_path`, never by name. It canonicalizes that path on a worker that `repo remove` waits on, as `repo add` waits on `add_repo`.
- `create_session(request)`:
  1. Validate the request before any git or tmux call. Without an agent, use the first `[[agents]]` entry. Refuse with a validation error that names the config path when no agent is configured. Also refuse when the agent's `command` does not resolve through `HostProbe::resolve_command`, when the worktree root is not writable, or, when it does not exist yet, its nearest existing ancestor is not writable, or when a non-empty prompt goes to an agent whose `prompt_args` holds no `{prompt}` (section 8).
  2. Check availability. The slug is unused by registry entries and live tmux sessions, `<worktree_root>/<repo>/<slug>` does not exist and is neither a registry entry's worktree path nor a path that `list_worktrees` shows for the repo, and `<branch_prefix><slug>` does not exist (`branch_exists`). All three are checked before any git call that changes state.
  3. Resolve the start point lazily, for this repo only (section 8).
  4. Create the worktree and branch with `--no-track`, or `--orphan` for an unborn HEAD. If `git worktree add` fails, remove the worktree with `git worktree remove --force` when `list_worktrees` shows the target path, then delete the branch if git created it. When that entry is locked, first run `git worktree unlock <path>` through `Workspace::unlock_worktree`, because a `git worktree add` killed with SIGKILL during checkout leaves its new worktree locked, and step 2 proved that this creation made the worktree at that path. A failing post-checkout hook in the user's repo makes git exit nonzero after creating both, and it counts as a creation failure.
  5. Create the detached tmux session in the worktree in one invocation. It runs the launcher with a handoff file, tags the agent pane `@ringleader_agent`, sets `remain-on-exit on` on the agent pane, sets `destroy-unattached off` on the session, writes `@ringleader_meta`, applies the `-x/-y` size, and ends with `display-message -p -t =<session>: 'ringleader-done #{pane_id} #{exit-unattached} #{socket_path}'`, with the socket path last since it can contain spaces. When a user hook split the window and the two pane ids differ, a second invocation moves the tag and `remain-on-exit` as section 2 describes. A server with `exit-unattached` on fails the creation (section 2). On failure, the adapter has already killed what the invocation created, and the use case removes the worktree and branch from step 4. A timed-out invocation can stop before it prints any id and can still create the session later, so after a timeout the use case first calls `kill_session`, which targets `=<session>:`, ignoring a missing session, and keeps the worktree and branch when that call also times out (section 9).
  6. Persist.
  The agent argv is `command`, then `args`, then `prompt_args` expanded with the request's prompt (section 8). The prompt is not stored in the session or registry. `create_session` never touches key bindings.
- `config()`: the loaded `Config`, read-only. The `n` dialog takes its agents from it, in config order, and marks those whose `prompt_args` holds no `{prompt}`. `App` takes the timer intervals and `bell_on_waiting` from it, and reads it again after `reload()`.
- `delete_impact(name)`: read-only. It applies the refusals of `delete_session` step 1 and the step 2 refusal for a worktree git cannot measure, then returns the `DeleteImpact` that step 2 computes, through the same code, and kills, removes, and persists nothing. The `d` dialog opens with it. The TUI never calls `delete_session` before the user confirms, because `delete_session` deletes a session with nothing to warn about without asking.
- `delete_session(name, confirmation)`: `confirmation` is a `DeleteConfirmation` support type. It holds the `DeleteImpact` the user saw, or `Force` for CLI `--force`, which accepts `Working`, any count, and every nested repository and process. It also holds a `forget` flag for CLI `--forget`. CLI `delete` without `--force` passes an empty `DeleteImpact`.
  1. Refuse `Unmanaged` sessions with a conflict. Refuse with a conflict when `caller_session` is the target, because killing it would end the deleting process partway through. Refuse with a conflict when a `Stopped` session is live on its recorded socket (`has_session_on`, section 8).
  2. Re-check the guards at execution time. First refuse with a conflict that names the repo path and the worktree path when git cannot measure the worktree. git cannot measure it when `validate_repo` fails on the repo path, or when the worktree directory exists but `list_worktrees` does not list it or its `.git` is missing or is not a file. Step 4 also refuses those worktree cases. The refusal says to restore the repository, remove a leftover worktree directory by hand, or delete with `forget`. Then compute a `DeleteImpact { dirty_files, nested_repos, unmerged_commits, processes, working }` support type: the `dirty_state` count and nested repository paths, the `unmerged_commits` count, the processes that `processes_in` finds in the worktree, excluding the sessions led by the live session's `pane_pids`, and whether the state is `Working`. A missing worktree counts as zero dirty files. Record the tip and HEAD that `unmerged_commits` counted from. Unless the confirmation is `Force`, refuse with a conflict that carries the current `DeleteImpact` when the state is `Working` and the confirmation's `working` is false, when a count that was zero in the confirmation is now positive, when the confirmation's `working` is false and a count grew, or when a nested repository or a process is not in the confirmation. With `working` confirmed, a confirmed nonzero count may grow, since the agent keeps writing while the user confirms. A count does not see one file replaced by another, so this catches added work, not every edit.
  3. Refuse filesystem and branch operations when the worktree path is not strictly inside the entry's recorded canonical `worktree_root`, or the branch does not start with the entry's recorded `branch_prefix` (section 8). Containment canonicalizes the nearest existing ancestor of `worktree_root` and of the worktree path through `HostProbe::canonicalize_lenient`, appends the remaining components of each, and rejects any `..` component, so a missing worktree directory or a missing worktree root still passes.
  4. Check that git will accept the removal before touching anything. Refuse when `list_worktrees` shows the path as the main worktree or a locked worktree, when the path exists but git does not list it, or when the branch is checked out in a worktree other than the session's. Also refuse when the worktree directory exists but its `.git` is missing or is not a file, since `git worktree remove --force` refuses both. `list_worktrees` marks a worktree whose `.git` is missing as `prunable` even though its directory exists, so this step checks the directory on disk, and no step reads the `prunable` flag. `is_file` cannot catch a `.git` file that names a git directory other than the worktree's own, such as another worktree's admin directory. git refuses it at step 6, after step 5 has stopped the agent, and the session stays `Stopped` with its branch and registry entry. Any other broken `.git` file makes `dirty_state` fail in step 2, before anything is stopped. Log the tip and HEAD that step 2 recorded at info level, with the session name, because step 6 deletes the worktree's HEAD reflog and Ringleader can die while git finishes step 6.
  5. Stop every process that could still write. When the session is live, read every pane's `#{pane_pid}` with `pane_pids`, then run `kill_session`. When either call times out, stop and keep the worktree, the branch, and the registry entry (section 9). Each pane process leads its own session, so its `nohup` children keep its session id. `terminate` then sends SIGTERM to every process that `session_processes` finds in those sessions and to the confirmed outside processes that step 2 found. A `Stopped` session has no panes, so only the confirmed outside processes are stopped. If `terminate` returns a survivor, or `processes_in` with no sessions excluded still finds a process in the worktree, stop with a conflict that names each pid and command, and keep the worktree, the branch, and the registry entry. The session is now `Stopped`, so a retry re-runs the guards. Then call `unmerged_commits` again. When its tip or HEAD differs from the step 2 record, including an unborn branch that now has a commit, or its count grew, stop the same way with a conflict that names both SHAs.
  6. Remove the worktree with `git worktree remove --force`. On git 2.42 and newer it also unregisters a worktree whose directory is already gone, so Ringleader never runs a repo-wide `git worktree prune`. When `list_worktrees` no longer lists the path, skip this step. If git fails, call `list_worktrees` again. When it still lists the path, stop with git's stderr, and keep the branch and the registry entry. When it does not, the removal was partial. Stop with git's stderr, the leftover path, and the SHAs step 2 recorded, keep the branch and the registry entry, and tell the user to remove the leftover directory by hand. The next delete then finds the directory missing and completes.
  7. Delete the branch with `delete_branch`, passing the tip step 2 recorded. When git refuses, stop with its stderr, keep the branch and the registry entry, and say that the worktree was already removed, so a retry skips step 6 and finishes. An unborn branch has no ref to delete, and an already-missing branch is tolerated, so both call `delete_branch` with no expected tip. It skips `update-ref` and removes only a leftover `branch.<branch>` section, which a delete that died between `update-ref` and `--remove-section` leaves behind.
  8. Remove the registry entry and persist.
  With `forget`, delete applies step 1 and the `Working` check of step 2, kills the tmux session if it is live, removes the registry entry, and runs nothing else. It reports the worktree path and branch it left on disk, which `doctor` then lists as orphans. Use `forget` when the repository moved or was deleted.
  Return the deleted tip SHA, plus the worktree HEAD SHA when it differs, so the CLI can print them and the user can recover with `git branch <name> <sha>`. Also return the `DeleteImpact` that step 2 computed. CLI `--force` prints it to stderr as its warnings. An unborn branch returns no SHA, and the CLI prints that the session had no commits. A missing branch also returns no SHA, and the CLI prints that the branch was already gone and that an interrupted earlier delete logged its SHAs in `app.log`.
- `rename_session(old, new, keep_branch)`: refuse `Unmanaged` sessions. The new tmux session name and branch use the entry's recorded prefixes (section 8). Validate the new name for availability on the slug and the tmux session name, and, unless `keep_branch`, fail early if the target branch exists. Rename the branch first, in the worktree, or with `git -C <repo>` when the worktree is missing. For a live session, then call `rename_session`, which renames the tmux session and refreshes `@ringleader_meta` in one invocation. A `Stopped` session has no tmux session, so it skips that step. Persist the registry last. When the tmux invocation prints no `ringleader-done` line (section 2), roll the branch rename back so the pair stays consistent. After a tmux timeout, rename instead keeps the renamed branch and persists nothing (section 9). A `Stopped` session has no `@ringleader_meta` for re-keying to read, so when its registry write fails after a branch rename, roll the branch rename back too. A live session whose registry write fails keeps its new names, and the error says that the next TUI run or mutating session command records them through re-keying (section 8). When a rollback fails, report both errors and name the branch git now holds. A `Stopped` session that is live on its recorded socket refuses with a conflict (`has_session_on`, section 8). Never touch the worktree directory.
- `attach(name, return_mode)`: `return_mode` says whether to ensure the Ctrl-Q return binding first; the TUI passes `InstallReturnBinding`, the CLI passes `None`. Then `Multiplexer::attach`, which targets the tagged agent pane. The facade reports the injected inside-tmux flag, and the UI wraps the call in `TerminalGuard` only when it is false. The CLI calls `attach` directly. Unmanaged sessions listed in the UI are attachable, not restartable or deletable.
- `open_shell(name, return_mode)`: if the tmux session is live, `ensure_shell_window` creates or finds a window identified by the window user option `@ringleader_shell` (not by name, since `allow-rename` can rename it), running `$SHELL` in the worktree, and returns its `window_id`. A new shell window is created without `-d` and tagged in the same invocation, so `=<session>:` resolves to it, and its id comes from the `ringleader-created` line (section 2). `Multiplexer::attach` then targets `AttachTarget::Shell(window_id)`, with the same `attach-session` or `switch-client` split as `attach`. A missing worktree fails before tmux runs, pointing to `doctor`. The window persists like any other. If the tmux session is stopped, return an ephemeral shell request (`$SHELL`, cwd = worktree) for the UI to run under the terminal guard. Unmanaged sessions have no trusted worktree path, so `t` is disabled for them with a status-bar message.
- `restart(name)`: both `Exited` and `Stopped` restarts check the worktree directory through the `HostProbe` port before tmux runs, and a missing worktree fails with a message pointing to `doctor`. tmux never catches it, since `new-session`, `new-window`, and `respawn-pane` all start the pane in `$HOME` and exit 0. A worktree directory that exists but that `list_worktrees` does not list, or whose `.git` is missing or is not a file, such as the leftover of a partial removal, fails the same way, because the agent's git commands there could reach the repository that encloses `worktree_root`.
  - `Exited`: `respawn_agent` writes a fresh handoff file and runs `respawn-pane` on the tagged agent pane by `pane_id`, passing the launcher command explicitly and never relying on the pane's original invocation. If the session has no tagged agent pane, `respawn_agent` creates a new window running the launcher, without `-d`, and in the same invocation tags its pane and sets `remain-on-exit on`, so `=<session>:` resolves to the new window.
  - `Stopped` with the tmux session gone: `create_session(spec)` recreates it under its recorded tmux session name in the existing worktree with the same single-invocation configuration. The registry entry records the socket path that `create_session` returns and is persisted. When that write fails, restart kills the recreated session and fails, so the entry never keeps a stale socket path. A `Stopped` session that is live on its recorded socket refuses with a conflict (`has_session_on`, section 8).
  - `Working` and `Waiting` refuse with a conflict, and `Unmanaged` sessions cannot be restarted.
  Restart never removes, resets, or recreates the worktree or the branch, and a failed restart leaves the registry entry unchanged and the session `Stopped` or `Exited`. Restart builds the agent argv from `command` and `args` only and never replays the initial prompt, even if one was used at creation. If the session's agent no longer exists in config, or its `command` does not resolve through `HostProbe::resolve_command`, fail before tmux runs with a clear message and a doctor finding (section 8).
- `ring_bell()`: delegates to `Multiplexer::ring_bell`.
- `repair_return_binding()` and `release_return_binding()`: called by the TUI at startup and exit.
- `doctor()`: see section 7.

- Navigation with arrows and `h`/`j`/`k`/`l`. Selection is tracked by `SessionName`, never by row index, so rows changing state do not move the cursor.
- Right panel: live preview via `preview(name)`, which runs `tmux capture-pane -e -p` on the tagged agent pane on its own `preview_refresh_ms` timer, independent of the state poll, and again immediately when the selection changes. There is no `-J`, so every captured row is at most the pane's width. The preview trims trailing blank rows, shows the last rows that fit, anchored to the bottom where agents keep their prompt, and clips on the right without wrapping. Render ANSI through `ansi-to-tui`, fall back to plain text if parsing fails. On capture failure show session metadata. A nonzero exit counts as a capture failure only when stdout is empty, because a failing `after-capture-pane` hook makes tmux exit nonzero after a full capture. Any hook output shows at the bottom of the preview, which v1 accepts.
- Diffs are computed only for visible rows, through `diff_stats(names)`, never for the whole registry on every tick. The event loop ticks every 100 ms. It polls input until the next tick deadline, then runs the timers that are due. `diff_stats` runs git on the event-loop thread. Every `diff_refresh_ms`, the TUI queues each visible row that is not already queued, and it drops a queued name once its row is no longer visible or its session is gone. The queue therefore never holds more names than there are visible rows, and when git is slower than the timer, every visible row still refreshes in turn. Each tick, `App` passes queued rows to `diff_stats` one name per call, at most two per tick, and makes no further call once 50 ms have passed in the tick. A pass over twenty rows then spreads over several ticks instead of freezing input. One slow row still blocks input until each of its git calls finishes or times out (section 9). Section 16 names the worker thread to add if that stalls input on large repos. Twenty sessions must not spawn forty git processes per tick.
- Status bar lists keys and transient errors with the fixed order and width-based dropping described in the responsive tiers: `n` new, `d` delete, `R` rename, `Enter` attach, `t` shell, `s` restart, `r` refresh, `?` help, `q` quit.
- Create, delete, rename, and restart block the event loop while git and tmux run, so the UI first draws a frame with a busy message in the status bar.
- Sort order: state priority `Working`, `Waiting`, `Exited`, `Stopped`, `Unmanaged`, then name. Stable across refreshes because selection is name-based.
- Terminal-too-small guard: the TooSmall tier below 36x8, see the responsive tiers above. There is no fixed 80x24 cutoff; tiers scale all the way down.
- `n` dialog: name field, repo picker, agent picker, an optional initial prompt field, and an "Add repo" row. The agent picker lists the agents from `config()` in config order and preselects the first. With no agents configured, the dialog shows `no agents configured in <config path>` in place of the agent picker and cannot be submitted. A non-empty prompt for an agent whose `prompt_args` holds no `{prompt}` is refused in the dialog with the message `new` prints (section 8). The prompt field is one row tall and is submitted with the session. It can hold line breaks from a paste, shows each as `⏎`, and passes them to the agent as part of the prompt text, which `prompt_args` expansion never splits. Leaving it empty creates the session with no initial message. The picker lists `discover_repos` for the launch scope, with explicit config overrides merged in and marked. When two rows share a repo name, each also shows its canonical path, truncated from the left. The dialog passes the selected repo's path to the service, never its name. The resolved scope path is shown at the top of the picker and can be changed with a path input, read as a typed path (section 8). While the scan runs, the picker shows `Scanning <scope>` and every key keeps working. The picker also says when the scan was cut short or the walk-up met a linked worktree git cannot resolve.
- Empty picker state: when the scope contains no repos, show "no repos found in <scope>" with two actions: "Add repo" and "Change scope". When the scope root cannot be listed, show that error with the same two actions. No silent fallback to `$HOME`.
- "Add repo" row: opens a path input, reads it as a typed path (section 8), draws a busy message in the dialog, and validates it with `git -C <path> rev-parse --path-format=absolute --show-toplevel --git-dir --git-common-dir --show-superproject-working-tree`. It rejects a linked worktree, where the git dir differs from the common dir, and a submodule, where the superproject is not empty, because `--show-toplevel` alone accepts both. Outside a submodule git prints no superproject line, so the output has three lines for a repository and four for a submodule. It stores the canonical top level rather than the typed path, and appends an explicit override to the config with `toml_edit` through `add_repo`, passing no name. Given no name, `add_repo` derives one from the top level's slugged basename. When the repo is already configured, it returns that entry whatever its name. The row then reloads the picker and selects the new repo or the existing entry. When `add_repo` refuses because another explicit entry already uses the derived name, the row shows a name field prefilled with it and saves only a name no explicit entry uses. This is the fix for the claude-squad pain point. Adding is optional: scanned repos already work without config entries.
- `d` dialog: opens with `delete_impact(name)`, which blocks while git and tmux run, so the UI first draws the busy message. When it returns, the event loop drops the queued key and paste events as after a delete, so a key typed ahead cannot confirm a dialog the user has not seen. A refusal, such as for the session the TUI itself runs in, shows in the status bar instead of a dialog. When git cannot measure the worktree, the message also says that `ringleader delete <name> --forget` needs the TUI to quit first, since the TUI holds the lock. The dialog shows name, branch, worktree, and diff. A dirty worktree shows "N uncommitted files will be lost" and names each untracked nested repository and says that delete removes its files, and also its local commits when its `.git` is a directory. Commits on no other ref, in the branch, the worktree HEAD, or a submodule, show "N commits exist on no other ref and will be lost". Each process outside the session that runs in the worktree is named with its pid and command, with a note that delete sends it SIGTERM and stops if a process survives it, such as an interactive shell. Any of these requires a second confirmation. A `Working` session additionally warns "agent is actively working". The dialog always states that ignored files such as `.env` are deleted with the worktree, since the dirty count leaves them out. Confirming passes the `DeleteImpact` the dialog showed. When step 2 refuses because the state changed after the dialog opened, the dialog reopens with the `DeleteImpact` the refusal carries. Other refusals show in the status bar. After a delete, the status bar shows the deleted tip SHA, and the worktree HEAD SHA when it differs, that the session had no commits, or that the branch was already gone and that an interrupted earlier delete logged its SHAs in `app.log`.
- `R` dialog: old and new name fields plus a "rename branch" toggle, on by default. The dialog shows the branch rename that will happen.
- `r`: `reload()` config and registry from disk, read `config()` again, and refresh diffs and observations. When the file fails to parse or fails a load check, `r` keeps the previous config and shows the error in the status bar (section 8). While the TUI runs read-only on the defaults because its config failed, `n`, `d`, `R`, and `s` show the config error in the status bar and do nothing else, opening no dialog, until `r` loads a config that passes.
- `t`: open a terminal in the selected session's worktree. If the tmux session is live, create or select the shell window (identified by `@ringleader_shell`, so a user rename cannot break it) in that session, running `$SHELL` in the worktree directory, and attach the client to it, so it persists like any other tmux window. If the tmux session is stopped, suspend the TUI and run an ephemeral `$SHELL` in the worktree, returning to the TUI on exit. Uses the same terminal guard as attach. `$SHELL` is the value `main` passes to `SessionAccess`, with `sh` as fallback. Disabled for unmanaged sessions. With no session selected, `t` shows a status-bar message and does nothing.
- `s`: restart the selected session. `Exited` sessions get `respawn-pane`; `Stopped` sessions get their tmux session recreated in the existing worktree. Disabled for `Working`, `Waiting`, and `Unmanaged` with a status-bar message.
- `q`: quit the app. tmux sessions keep running in the background; the next launch reconciles and lists them again.
- `?` help dialog: key bindings, config and log paths, version, and the Ctrl-Q behavior including the inside-tmux caveat. It says that a terminal emulator started in the foreground of a tmux pane counts as inside tmux, and that `env -u TMUX -u TMUX_PANE ringleader` forces outside mode against the default server (section 2). It also tells the user to open extra shells with `t` instead of splitting the agent window, since output in a split pane counts as agent activity. Centered overlay, closed with `?`, `Esc`, or `q`.
- Bell: when `bell_on_waiting` is enabled, `App` keeps the previous state per session and asks `SessionState`'s edge predicate whether the new state is a `Working` to `Waiting` transition. On that edge, it rings unless the session's summary has `attached` set, which means a client shows the agent window. A client on the agent window suppresses the bell because typing into the agent also moves `window_activity` and the user is already looking at it. A client on the `t` shell window of the same session does not count, because typing there moves only the shell window's `window_activity`. No bell for `Exited`. While an outside-tmux attach child runs, the TUI is suspended and does not poll, so the bell fires only inside tmux or while the home screen is shown. The help dialog states this.
- Bell delivery: outside tmux, `App` writes one BEL byte to its own terminal through a bell sink, a `Box<dyn Write>` that it takes through its constructor, then flushes and ignores write errors, since the terminal may already be gone. `main` passes `std::io::stdout()`, and tests pass an in-memory buffer. Inside tmux, `App` calls `ring_bell()`, which writes BEL to the tty of every client on the server, so it reaches the user in any session, even when the TUI's pane is hidden. `ring_bell` runs `list-clients -F` with a fixed label, `#{client_control_mode}`, and `#{client_tty}`, tab-separated, reads only the labeled rows (section 2), and skips every client whose `client_control_mode` is 1 or whose `#{client_tty}` is empty. A control-mode client started from a terminal, such as iTerm2's `tmux -CC`, reports a real tty that carries the control protocol. `ring_bell` opens each tty with `OpenOptions::new().write(true)` and `custom_flags(libc::O_NONBLOCK | libc::O_NOCTTY)`, since a blocking write would freeze the event loop on a client whose tty output is stopped or full. A failed open or write on one client, such as `WouldBlock`, `PermissionDenied` for another user's client under `server-access`, or `NotFound` for a client whose terminal closed after `list-clients`, is logged at debug level and skipped, so the other clients still ring. Only a `list-clients` call that times out, or that exits nonzero with no labeled line, is an adapter error, since a failing `after-list-clients` hook makes tmux exit nonzero after a full listing.
- Event loop drains `Event::Resize` and forces a full redraw, so the too-small guard clears and recalculates when the terminal grows.
- Paste: `TerminalGuard` enables bracketed paste with crossterm's `EnableBracketedPaste` whenever it enters raw mode, including each resume after an attach or an ephemeral shell, and sends `DisableBracketedPaste` whenever it leaves raw mode, including on exit and on panic. Without it, the terminal sends a paste as keystrokes and each line break as Enter, so a multi-line prompt would submit the `n` dialog at its first line. An `Event::Paste` goes whole to the focused text field and is ignored everywhere else. Pasted `\r\n`, `\r`, and `\n` all count as line breaks. The prompt field stores each as `\n`, and only a typed Enter submits the dialog. A name field turns each line break into a space, which the slug maps to `-`. A path field trims leading and trailing whitespace and line breaks from a paste, and a line break left inside the pasted path is a field error. When a create, delete, rename, or restart returns, the event loop drops the key and paste events queued while it ran and keeps a queued resize. Keys typed behind the busy message, or the rest of a paste on a terminal without bracketed paste, would otherwise run as home-screen commands.

Attach and Ctrl-Q:

- `main` computes the inside-tmux flag once (section 2). Outside tmux: terminal guard leaves raw mode, bracketed paste, and the alternate screen, runs `tmux attach-session -t <agent pane_id>` as a child, and after it returns re-enters raw mode, bracketed paste, and the alternate screen and calls `terminal.clear()`. Re-entering the alternate screen blanks it while ratatui still holds the previous frame and repaints only changed cells, so without the clear the home screen comes back empty. The ephemeral `t` shell resumes the same way.
- The outside-mode `attach-session` child is waited on with `libc::waitpid` and `WUNTRACED`, never `Child::wait`, which never returns once the client stops itself, as tmux's default `prefix C-z` (`suspend-client`) makes it do. When the child stops, Ringleader stops itself with SIGSTOP so the user's shell takes the terminal back. Once `fg` resumes it, Ringleader sends SIGCONT to the child and keeps waiting. `TmuxMultiplexer::attach` owns this wait, so CLI `attach` behaves the same, and its `waitpid` and `kill` calls form that method's one `unsafe` block. The ephemeral `t` shell is waited on with `Child::wait` instead, because zsh's `suspend` already stops Ringleader's whole process group and the `waitpid` loop would stop Ringleader a second time after `fg`. v1 accepts that bash's `suspend` leaves the terminal unread until bash gets SIGCONT from another terminal.
- Inside tmux: run `tmux switch-client -t <agent pane_id>`. The TUI keeps running and polling. `attach-session` cannot be used from inside tmux by a child process; it fails with "sessions should be nested with care".
- `t` uses the same paths: live sessions get the shell window and the outside/inside attach split, stopped sessions get an ephemeral `$SHELL` under the terminal guard. Ctrl-Q returns to the TUI from the shell window too, since the binding matches on managed session names.
- Ctrl-Q is chosen as the return key over Ctrl-D because Ctrl-D is meaningful to the agents themselves, such as EOF to exit Claude Code, so intercepting it would break the session.
- Only the TUI installs the binding. CLI `new` and `attach` never touch bindings, so a session attached from the CLI receives Ctrl-Q as a normal key unless a TUI is running.
- The binding embeds its return target, so it never depends on `client_last_session`, which changes as soon as the user switches sessions inside tmux:
  - Outside tmux: `bind-key -T root C-q if-shell -F '#{m:<prefix>*,#{session_name}}' 'detach-client' 'send-keys C-q'`. Detaching ends the attach child and the TUI resumes.
  - Inside tmux: `bind-key -T root C-q if-shell -F '#{m:<prefix>*,#{session_name}}' 'switch-client -t <tui_pane_id>' 'send-keys C-q'`, where `<tui_pane_id>` is the injected `$TMUX_PANE` (such as `%5`). A pane target selects the TUI's window and pane and survives a rename of the TUI's session. It also works when the TUI runs in a window of a managed session, where a session target would switch to the session already shown. Before installing, Ringleader confirms the pane with `display-message -p -t <tui_pane_id> 'ringleader-pane #{pane_id}'` and requires the labeled value to equal the pane id, because `display-message` exits 0 with an empty value for a missing target. When `$TMUX` is set but `$TMUX_PANE` is not, as in a `display-popup`, the TUI installs no binding and says so in the status bar.
  - Each branch is passed as one quoted command string. The brace form (`{ ... }` passed as separate arguments) fails on 3.6a with `unknown command` or `too many arguments`; do not use it. The prefix pattern is built from `tmux_prefix` at runtime, which config validation restricts to `[a-z0-9-]` so it cannot break the format string. `send-keys C-q` does not recurse. The pattern matches the current `tmux_prefix` only, so Ctrl-Q does not return from a session created under an earlier prefix, and `doctor` names such sessions (section 8).
- Install timing: `start-server` cannot keep a server alive with no sessions (`exit-empty`), so there is no server bootstrap step. The TUI calls `install` immediately before every attach, switch, or shell open, when the target session guarantees a running server. `install` saves the previous binding only when it holds no record for this server's socket path and pid, so it reuses a record that a failed `repair_stale` kept. When the binding it would save is recognizably Ringleader's, it records C-q as unbound instead, so exit never leaves Ringleader's binding behind. When the current root C-q matches the binding it would install, `install` binds nothing. It compares the fields described under Restoring against the command text tmux 3.6a and 3.7b list for that binding: `if-shell -F "#{m:<prefix>*,#{session_name}}" detach-client "send-keys C-q"` outside tmux and `if-shell -F "#{m:<prefix>*,#{session_name}}" "switch-client -t <tui_pane_id>" "send-keys C-q"` inside tmux. A binding is recognizably Ringleader's when its command text has either shape for any prefix matching `^[a-z0-9-]+-$`, so a `tmux_prefix` change after a crash never makes a stale Ringleader binding look like the user's. One that runs another command, such as a stale pane target or the other attach mode, is replaced without being saved as the user's binding. A fresh server started after the TUI launched gets the binding on the next attach.
- Saving the previous binding: before the first install on a server, `TmuxReturnBinding` runs `list-keys` with no arguments and selects the line that starts with `bind-key`, optionally `-r`, then `-T root C-q`, allowing any run of whitespace between tokens. That line is saved verbatim. No matching line means unbound. A nonzero exit aborts the install with a status-bar error only when the output holds no `bind-key` line, because a failing `after-list-keys` hook makes tmux exit nonzero after a full listing. The idempotence check in `install` and the check in `repair_stale` read the current root C-q the same way. Filtering the listing is not portable. On a 3.7 server, `list-keys -T root C-q` and `list-keys -T root -1 C-q` print nothing and exit 0 whether or not C-q is bound, and `list-keys -T root` prints nothing when the root table holds exactly one binding. The behavior follows the server's version, not the client's. The record in `$XDG_STATE_HOME/ringleader/bindings.json` holds the server's `#{socket_path}` and `#{pid}` with the saved binding.
- Restoring: an unbound record runs `unbind-key -T root C-q`. A bound record pipes the saved line to `tmux source-file -` and closes stdin, since the saved line uses tmux quoting and cannot be replayed as argv. It never passes a file path, because `source-file` treats every path as a glob(7) pattern, with or without `-F`, and a state directory containing a bracket expression such as `[1]`, or a `\`, would fail with `No such file or directory`. Ringleader then lists the bindings again and requires the C-q line to match the saved line field by field: the optional `-r`, the table, the key, and the command text, which starts at the first non-space character after the key. Whole lines are never compared, because tmux pads the table and key columns of the full listing to the longest names on the server, so the padding changes whenever a binding with a longer table or key name comes or goes. On a failure or a mismatch, it unbinds C-q, logs the saved line, and hands it to an exit notice. The binding guard and the exit notice are support types of `App` in `app.rs`. `main` creates the notice before the terminal guard, so the notice drops after it, on a normal exit and on a panic alike. On drop, the notice writes the line to stderr with `writeln!`, ignoring write errors, so the user can rebind it by hand. The binding guard never prints, because text written while the TUI holds the alternate screen vanishes when the terminal guard leaves it. Restoring a multi-line brace binding always fails on tmux 3.6a, which lists it with a doubled `\;\;` that `source-file` rejects. `list-keys` without `-N` never prints a binding's note, so a restored binding loses it. The TUI's binding guard restores on exit and on panic, before the terminal guard runs.
- Crash safety: `TmuxReturnBinding` writes `bindings.json` like the registry, through a synced temp file renamed over it and a synced directory. The record reaches disk before `bind-key` runs, and a failed write aborts the install with a status-bar error. At startup, `repair_stale` treats an empty or unparsable `bindings.json` as no record, logs a warning, and removes the file. Otherwise it checks the recorded server with `display-message -p 'ringleader-pid #{pid}'` on the recorded socket, which answers on a live server even with no sessions. When the pid matches and the root C-q is still recognizably Ringleader's, it restores the saved binding. It discards the record once that restore completes. It also discards the record when tmux answers `no server running on <path>` or `error connecting to <path> (No such file or directory)`, reports another `#{pid}`, or finds the root C-q unbound or not Ringleader's, so a binding from an older server never overwrites the current server's config. Any other outcome, such as `Permission denied`, keeps the record, logs the error and the saved line, and shows a status-bar warning, and the next start retries. This covers SIGKILL and power loss, which the panic hook and signal handling cannot.
- The per-session `key-table` alternative is rejected, not deferred. Testing on 3.6a showed it bypasses root bindings entirely and swallows unbound keys rather than forwarding them to the pane, and it replaces the user's whole root table for managed sessions. Do not revisit it.
- Verification criteria: C-q returns to the home page from managed sessions in both outside-tmux and inside-tmux contexts, including after the user switches between two managed sessions first, and when the TUI itself runs in a window of a managed session. C-q still reaches non-managed sessions. All pre-existing root bindings are restored on exit and on crash, including after two installs in one TUI run, on both a tmux 3.6 and a tmux 3.7 server.

## 7. CLI

- Running `ringleader` with no subcommand starts the TUI, with the current directory as the launch directory. Any subcommand runs the CLI and never starts the TUI. `Cli` holds the parsed subcommand as an `Option`. `--config` and `--log-level` are global options (`global = true`), accepted with no subcommand and before or after one.
- `main` starts in this order. It captures the `ProcessEnvironment` snapshot and parses arguments into `Cli`. For `__exec-agent` it then builds only `AgentLauncher` and runs it, so that path loads no config, writes no first-run template, opens no log file, installs no panic hook or signal flags, takes no lock, and deletes no stale handoff files. Every other path creates the state directory (section 8), has `AgentHandoff` delete stale handoff files (section 8), and builds `FileLock` from the state path. With no subcommand, `main` takes the lifetime lock, and for a mutating command `Cli` takes the write lock. A held lock exits 3. Only then do `CompositionRoot`'s methods load config, compute the agent `env` union for `TmuxCommand`, and build the adapters, `SessionService`, and the `App` or the `Cli` dispatch.
- `list [--json]` reconciles in memory only and never writes. It computes diffs for every session. It is safe to run while the TUI is running. Only the TUI and mutating commands persist the registry. JSON output is an array of objects with `name`, `repo`, `branch`, `worktree`, `agent`, `state`, and `diff` (`files`, `insertions`, `deletions`, `untracked`, or `null` for unmanaged sessions).
- `new --name <n> --repo <r> [--agent <a>] [--base-branch <b>] [--prompt <text>]`. Without `--agent`, the first `[[agents]]` entry is used, and with no agents configured `new` exits 1 naming the config path. `--prompt` passes an initial message to the agent via the agent's `prompt_args`. A non-empty `--prompt` for an agent whose `prompt_args` holds no `{prompt}` exits 1 before any git call. `--repo` takes a discovered repo name or a path. A value that is `.` or `..`, starts with `~`, or contains `/` is a path, read as a typed path (section 8). Any other value is a discovered repo name first and a relative path second. A name that matches more than one discovered repo exits 1 and lists each match's canonical path, so the user passes a path instead. A path is validated like the "Add repo" row (section 6), so a linked worktree or a submodule is rejected. It is matched to `discover_repos` by canonical top level, so an explicit override still applies.
- `delete <name> [--force] [--forget]`. The CLI never prompts. Without `--force`, a dirty worktree, unmerged commits, a process outside the session running in the worktree, or a `Working` agent exits 3 and prints what would be lost, naming each nested repository and each process. With `--force`, all of them are confirmed and the warnings go to stderr. Either way it warns that ignored files such as `.env` are deleted with the worktree. Deleting the session the command runs in exits 3. When git cannot measure the worktree, such as after its repository moved, delete exits 3 and suggests `--forget`, which kills the tmux session and removes only the registry entry, leaving the worktree and the branch for `doctor` to report. A process that survives SIGTERM, or a commit that landed after the guards counted, exits 3 after the tmux session was killed. On success it prints the deleted branch tip SHA, the worktree HEAD SHA when it differs, that the session had no commits, or that the branch was already gone and that an interrupted earlier delete logged its SHAs in `app.log`.
- `attach <name>`. Runs `attach-session` or `switch-client` only. It takes no lock and never touches key bindings.
- `rename <old> <new> [--keep-branch]`.
- `restart <name>`, restarts an `Exited` or `Stopped` session.
- `restart`, `delete`, and `rename` exit 2 for an unknown name and 3 for an `Unmanaged` session. `restart` exits 3 for a `Working` or `Waiting` session and 1 when the session's agent is missing from config or its `command` does not resolve.
- `repo add <path> [--name <n>] [--base-branch <b>]` writes an explicit override for the path's canonical top level. When that repo is already configured, it prints `already configured as <name>` and exits 0. A `--name` or `--base-branch` that differs from that entry exits 3 and names it. A name that another explicit entry already uses exits 1 and names that entry. `repo remove <name>` removes an override and reports when the repo is only discovered by scanning. It refuses while any registry session's `repo_path` equals the override's canonical path, naming the sessions and suggesting `delete` first. `repo list` lists what `discover_repos` returns for the current scope, the same set the picker shows and `new --repo` accepts by name, and marks explicit overrides, including those outside the scope.
- `__exec-agent --handoff <path>`, hidden. Invoked by tmux through the launcher path that `main` injects (`current_exe` in production). Reads the handoff file, deletes it, `env_clear`s, sets the environment from the file plus the kept pane variables, sets `GPG_TTY` to the snapshot's terminal name or leaves it unset when there is none, sets the agent's directory to the worktree path from the file with `Command::current_dir`, and execs the agent argv from the file. It never calls `std::env::set_current_dir`, which in a test would move the working directory of every test thread. A missing worktree path exits nonzero before the command is built, since `current_dir` on a missing directory fails with the same `NotFound` error as a missing program. Never reads `config.toml`. Not documented in README.
- `doctor [--json]`, checks and reports:
  - tmux present, version >= 3.2, checked for the client with `tmux -V` and, when a server is running, for the server with `#{version}`. Both checks run through the program path from section 2, which `doctor` prints. The two versions can differ, since the Nix wrapper's client can drive a server that another tmux started, and the server's version decides behavior.
  - a running server whose `exit-unattached` is on, which makes creation fail (section 2)
  - git present, version >= 2.42 required for `worktree add --orphan`, `worktree`, and `branch -m` in worktrees, checked with `git --version` run through the program path from section 2, which `doctor` prints
  - the config parses and passes every load check (section 8), each failure its own finding
  - each configured repo path resolves via `git rev-parse` and canonicalizes
  - at least one agent is configured
  - each agent `command` resolves through `HostProbe::resolve_command` on the app's own `PATH`, which is the `PATH` the launcher passes to the agent. When an unresolved `command` contains whitespace, the finding says to move the flags into `args`.
  - each agent's non-empty `prompt_args` has an element containing `{prompt}`
  - config path writable, or reported read-only because it resolves into `/nix/store` or its canonical file cannot be opened for writing
  - worktree root writable, or, when it does not exist yet, its nearest existing ancestor writable
  - state directory writable
  - registry readable, with a corrupt file or a newer schema version reported on stderr
  - registry entries whose worktree or branch is missing. An unborn branch checked out in the session's worktree counts as present. An entry with no live session is the normal `Stopped` state and is not a finding. For each `Stopped` entry, `doctor` runs `has_session_on` against the recorded socket and reports an entry that is live there, naming the socket. An adapter error from `has_session_on`, such as `Permission denied`, is a finding and does not stop `doctor`. `doctor` also reports an entry whose worktree path a live session other than its own claims through valid metadata, naming that session. It reports an entry whose tmux session name is held by a live session that is not its own, because that session has no valid metadata, names another worktree, or runs on another socket, and gives the `tmux -S <socket> kill-session -t '=<tmux name>:'` advice from section 8.
  - registry entries whose worktree directory exists but that git does not list, or whose `.git` is missing or is not a file, such as the leftover of a partial removal, with the advice to remove the directory by hand or run `delete <name> --forget`
  - registry entries whose agent no longer exists in config
  - registry entries whose recorded `worktree_root`, `branch_prefix`, or `tmux_prefix` differs from the current config, noting that Ctrl-Q does not return from a session whose name lacks the current `tmux_prefix`
  - orphaned worktrees under the worktree root that no registry entry claims
  - orphaned branches matching `branch_prefix` with no worktree
- Exit codes, documented in README and `AGENTS.md`: 0 success, 1 user or validation error, 2 not found, 3 conflict, including a refused guard, an `Unmanaged` target, a session that is live and healthy, or the lock being held. Argument errors exit 1, not clap's default 2. `main` parses with `Cli::try_parse` instead of `Cli::parse`, prints an error with clap's `Error::print`, ignoring its result, and exits with the code `Cli` maps from it: 0 when `Error::use_stderr` is false, as for `--help` and `--version`, and 1 otherwise. Exit 2 always means a name that was not found. A mutating command interrupted by Ctrl-C before its use case starts never runs it. One interrupted during its use case finishes it and prints its result. Both then end by SIGINT, which a shell reports as status 130.
- JSON output uses stable lowercase state strings: `working`, `waiting`, `exited`, `stopped`, `unmanaged`.
- `--config <path>` and `$RINGLEADER_CONFIG` override for tests.
- Locking: `new`, `delete`, `rename`, `restart`, `repo add`, and `repo remove` take the write lock. `list`, `doctor`, `attach`, `repo list`, and `__exec-agent` take no lock.

## 8. Config, state, locking

Config is app-owned at `$XDG_CONFIG_HOME/ringleader/config.toml`. The first-run template is the block below as written: `worktree_root` and the `[[repos]]` example stay commented out, so the worktree root defaults to `$XDG_DATA_HOME/ringleader/worktrees` and no example repo is configured. Writes go through `toml_edit` so user comments and formatting survive. The config path is canonicalized before any write. If the canonical path is inside `/nix/store`, report "config is Nix-managed, cannot write" and continue with config writes refused, never fail. Otherwise the adapter first opens the canonical file for writing without truncating it. When that fails with a permission error, it reports "config is read-only, cannot write" and refuses config writes the same way, because a rename needs only directory permission and would replace the file anyway. A write then creates a temp file next to the canonical target with mode 0600, writes it, calls `sync_all`, gives it the target's permission bits, renames it over the target, and calls `sync_all` on the directory, as registry writes do. A symlinked config therefore stays a symlink and keeps its mode. A config that fails to parse or fails a load check is never rewritten.

- First run is any start where the resolved config file does not exist. Only the TUI and the mutating commands write the template, after taking their lock. They create the config directory with `create_dir_all`, canonicalize it for the `/nix/store` check, and write the template into it with `create_new`, since a missing file cannot be canonicalized. `list`, `doctor`, `attach`, `repo list`, and `__exec-agent` never write it. A failed template write, including `AlreadyExists` from a dangling symlink, is a warning in the status bar or on stderr, and the defaults apply.
- The defaults are the template's top-level values, with no repos and no agents. A key the file omits takes its default. A missing `agents` key means no agents, and Ringleader never substitutes the template agents.
- Before it dispatches any command except `__exec-agent`, `main` creates the state directory with `create_dir_all`, so it exists before either lock and `app.log`. When that fails, the TUI and mutating commands exit 1 naming the path, and read-only commands run without a log file. When opening or locking the lock file fails for a reason other than a held lock, the TUI and mutating commands exit 1 naming the lock path and the error.
- `base_branch` optional. Resolution ladder, each step checked with `git rev-parse --verify -q`: `git symbolic-ref -q refs/remotes/origin/HEAD`, then `refs/heads/main`, then `refs/heads/master`. When `git rev-parse --verify -q HEAD` fails because HEAD is unborn and no base resolves, creation runs `git worktree add --orphan -b <branch> <path>`. Otherwise a clear error asking for an explicit `base_branch`. An explicit `base_branch` names a local or remote-tracking branch, such as `main` or `origin/main`, and `new --base-branch` overrides the repo's value for that session. Resolution tries `refs/heads/<base_branch>^{commit}`, then `refs/remotes/<base_branch>^{commit}`, each with `git rev-parse --verify -q`, and never passes the bare name to git, whose own lookup prefers a tag of the same name. When neither resolves, creation fails with an error naming both refs, and suggests `origin/<base_branch>` when that ref resolves. This holds even when HEAD is unborn, since only the ladder falls through to `--orphan`. The resolved commit SHA becomes the session's base commit. Worktrees are always created with `git worktree add --no-track -b <branch> <path> <start>`. Local refs only, no fetch ever. Resolution is lazy, only for the repo the user actually picks.
- `state_poll_ms` drives observation and classification. The spinner advances once per tick (section 6). `preview_refresh_ms` runs the preview on its own timer, faster than the state poll by default, because it captures a single pane. `diff_refresh_ms` is the slow timer, and diffs are computed for visible rows only.
- Repo scanning: the scope resolves from the launch directory by walking up to the nearest `.git`, or to the launch directory itself when there is none. When the launch directory is inside a repo, including at its top level, the bounded walk also runs from the launch directory, and its results merge with the enclosing repo. Without that, a dotfiles repo at `$HOME` would hide every repo under `$HOME`. The same rule applies when the user changes the scope in the picker. A `.git` file met by the walk-up gets the "Add repo" `git rev-parse` check (section 6) in its directory. A submodule resumes the walk-up at its superproject's top level. With no superproject line, a git dir equal to the common dir means a `--separate-git-dir` repository, which is the enclosing repo. A git dir that differs means a linked worktree, which resolves to the parent of its common dir when `git -C <parent> rev-parse --show-toplevel` prints that parent, so launching from a managed worktree or a `t` shell still finds the repo. Otherwise, as for a worktree of a bare or `--separate-git-dir` repository, git records no main work tree and `git worktree list` shows the git dir in its place, so the walk-up ends with no enclosing repo and the picker says so. A `.git` file whose check fails, such as one whose git dir was deleted, ends the walk-up the same way.
- The walk is depth-limited by `scan_depth` (default 3). The scope root, where the walk starts, is depth 0, and a repo is found when its top-level directory is at depth `scan_depth` or less, so with the default, `<scope>/a/b/example-project` is found and `<scope>/a/b/c/example-project` is not. The walk goes breadth first and reads each directory's entries sorted by name, so when the visit cap stops it, every repo at a smaller depth has already been found. Below the scope root it never descends into a directory whose name starts with `.`, or into `node_modules`, `target`, `vendor`, or `dist`, but the `.git` check still runs in every visited directory. It never enters `/proc`, `/sys`, `/dev`, or `/nix/store`. Below the scope root, a `.git` directory marks a repo and stops descent. Below the scope root, a `.git` file gets the same `git rev-parse` check: a linked worktree or a submodule is skipped, and a `--separate-git-dir` repository is listed and not descended into. The walk does not follow symlinks. It skips any directory whose listing, entry read, or `.git` check fails, whatever the error, such as `EACCES`, `ENOENT` from a directory removed mid-walk, `ENOTCONN` from a dead FUSE mount, `ESTALE`, or `EIO`, and never matches on the error kind. The walk finds `.git` in each visited directory's own listing, so a directory without one is not a failure. Only a scope root that cannot be listed fails the scan. The walk stops after visiting 5,000 directories, and the picker and `repo list` say that the scan was cut short. Results are canonical paths, deduped, and held by the `n` dialog until it closes, so every opening scans afresh.
- Below the scope root, the walk never enters or stats a mount point whose filesystem type in `/proc/self/mountinfo` starts with `fuse` or is `nfs`, `nfs4`, `cifs`, `smb3`, `9p`, `ceph`, or `autofs`. One `readdir` or `lstat` on a hung network or FUSE mount blocks in the kernel with no timeout. The scanner reads the table once per walk, decodes its octal escapes, and checks each entry's path against it before any other call on that entry, since even `DirEntry::file_type` falls back to `lstat` when the filesystem reports no `d_type`. `resolve_scope` canonicalizes the directory it is given before the walk-up. The table lists canonical paths, and a typed scope can contain a symlink or `..`, whose textual parents are not its ancestors. A scope root on such a mount is still walked. When the table cannot be read, nothing extra is skipped. Repos on a skipped mount, including local FUSE filesystems such as `gocryptfs`, are reached through "Change scope", "Add repo", or `[[repos]]`.
- Typed paths: `RepoCatalog` reads the picker's scope input, the "Add repo" input, a `new --repo` value that section 7 treats as a path, and `repo add` the same way, before it scans or runs git on the path. A leading `~` alone or `~/` expands to the snapshot's `HOME`, which `main` passes to `RepoCatalog`. A relative path joins the injected launch directory, never the process cwd. Nothing else expands, so `~user/x` and `$HOME/x` stay literal. The result must be an existing directory (`HostProbe::path_exists` and not `is_file`), or the TUI keeps the input open with "no such directory: <path>" or "not a directory: <path>" and keeps the previous scope and picker list, and the CLI exits 1 with the same message. `RepoCatalog` runs this check on a `std::thread` worker that the TUI polls and the CLI waits on, as for `discover_repos` (section 5), because a `stat` under a hung network or FUSE mount blocks with no timeout.
- `env` lists variable names. They add to a fixed baseline and never replace it. The baseline is `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, `XDG_*`, `SSH_AUTH_SOCK`, `KRB5CCNAME`, `TERMINFO`, `TERMINFO_DIRS`, `LOCALE_ARCHIVE`, `DISPLAY`, `XAUTHORITY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `BROWSER`, `EDITOR`, `VISUAL`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` with their lowercase forms, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NIX_SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, and `GNUPGHOME`. Without the display, browser, proxy, and CA names, agents lose browser login, clipboard access, and API access behind a proxy or a TLS-inspecting CA. `XAUTHORITY` travels with `DISPLAY`, because an X server whose cookie file is not `~/.Xauthority`, such as an SDDM X11 session or GNOME's Xwayland, refuses a client that cannot find the cookie. `GPG_TTY` is never copied, since it would name the wrong terminal. The launcher sets it to its own. At session creation and on restart, the tmux adapter reads the values of the baseline and the configured names from the injected `ProcessEnvironment` snapshot and writes them, with the agent argv and the worktree path, into the handoff file through `AgentHandoff`. Values never pass through domain or application. Missing variables produce a warning, not a failure. Values are never logged.
- Handoff files live in `$XDG_RUNTIME_DIR/ringleader/handoff/`, or `$XDG_STATE_HOME/ringleader/handoff/` when there is no runtime directory. `AgentHandoff` creates the directory with `DirBuilder::new().recursive(true).mode(0o700)` before every write rather than once at first run, because a reboot empties `$XDG_RUNTIME_DIR` while config, state, and the registry persist. Each file is created with `create_new` and mode 0600. The launcher deletes its file before exec. When `create_session` or `respawn_agent` fails, `TmuxMultiplexer` deletes the file it wrote, ignoring a missing file, before it returns the error. A failing user hook alone does not fail them (section 2), so the file stays for the launcher. tmux exits 0 even when the launcher never runs, so `AgentHandoff` also deletes the regular files in the directory last modified more than 60 seconds ago, treating a missing directory as empty. It does so before every write and once at startup of the TUI and of every CLI command, never in `__exec-agent`.
- Each `[[agents]]` entry has `command`, one program name or path that is never split or shell-evaluated, and an optional `args` array of strings, empty by default, passed verbatim with no `{prompt}` substitution. The agent argv is `command`, then `args`, then the expanded `prompt_args`, so `args` apply on every launch and restart. A leading `~/` in `command` expands like `worktree_root`. When an unresolved `command` contains whitespace, the refusal and the `doctor` finding say to move the flags into `args`.
- `prompt_args` is the argument template for an initial prompt. Expansion makes one pass over the template: each element becomes exactly one argv element, and every `{prompt}` inside it is replaced by the prompt text, which is never expanded again. So `["--prompt={prompt}"]` passes `--prompt=<prompt>` as one argument. Claude Code uses `["{prompt}"]` (positional), and opencode uses `["--prompt={prompt}"]`. The `=` form matters because opencode parses options with yargs, which reads a separate value that starts with `-` as another option, so `["--prompt", "{prompt}"]` would turn the prompt `- fix the tests` into an empty prompt. Claude Code's positional prompt and opencode 1.18.30's `--prompt` were verified against the installed versions. A prompt containing multiple words, quotes, or a trailing `;` stays one argv element, never split or shell-evaluated, because the argv travels in the handoff file and never on a tmux command line. When the prompt is empty, no prompt arguments are appended, regardless of the template. An absent or empty `prompt_args`, or one with no `{prompt}`, cannot carry a prompt, so a non-empty prompt for that agent is refused before any git call, with exit 1 from `new` and the same message in the `n` dialog.
- A `worktree_root` or `[[repos]]` `path` that is exactly `~` or starts with `~/` has that `~` replaced by `HOME` from the `ProcessEnvironment` snapshot at load. Nothing else expands, so a `~user` form and environment variables such as `$HOME` stay literal, and the load checks reject the relative result. `TomlConfigSource` keeps the expanded repo path, and `discover_repos` canonicalizes it on its worker (section 5), so a repo on a stalled network mount never blocks config loading. Resolution order for the config file: `--config` flag, then `$RINGLEADER_CONFIG`, then `$XDG_CONFIG_HOME/ringleader/config.toml` (falling back to `~/.config`). The first match wins, no merging.
- Config checks have two tiers. Load checks are pure, run on every load, including TUI startup, `r`, and every CLI command that reads the config, and name the key in every failure. An empty or first-run config passes every load check and must not block startup. No repo is required, since scanning supplies them, and no agent is required either. First run seeds the template with the two default agents, `claude` and `opencode`, so `n` works immediately. The bullets below, up to the use checks, are the load checks.
- `tmux_prefix` must match `^[a-z0-9][a-z0-9-]*-$` and `branch_prefix` must match `^[a-z0-9][a-z0-9-]*/$`. Neither may start with `-`, because `rename-session` and the `git branch` call behind `git worktree add -b` would read the name as options.
- Repo names use the `RepoName` alphabet. Repo names are unique among `[[repos]]` entries. Agent names are unique among `[[agents]]` entries. A scanned repo may share a name with an explicit entry, since repos are keyed by canonical path.
- `worktree_root` and every repo `path` must be absolute after `~` expansion. A value that starts with `$` fails with a message saying environment variables are not expanded.
- An agent `command` must be non-empty, and a `command` that contains `/` must be absolute after `~/` expansion, since the launcher execs from the worktree.
- `session_size` is `<width>x<height>`: two decimal integers joined by a lowercase `x`, with no spaces, width 20 to 500 and height 10 to 200. tmux would reject a bad size only after `create_session` step 4 has created the worktree and branch, and a very large pane slows every preview capture.
- `activity_idle_seconds` is an integer from 2 to 3600. Below 2, a pane that prints continuously can read as `Waiting`, because `window_activity` can be 1 second old.
- An agent `env` entry must be a plain variable name matching `^[A-Za-z_][A-Za-z0-9_]*$`, so a pattern such as `AWS_*`, an assignment such as `FOO=bar`, or an empty string fails with the agent and the entry named. A name listed twice in one agent counts once. An `env` name must not be a baseline name, which already reaches the agent. It must not be `TERM`, `COLORTERM`, `TMUX`, `TMUX_PANE`, or `GPG_TTY`, which the launcher takes from its own pane or sets itself, and which Ringleader must never remove from a tmux client. It must not be `MSYSTEM`, `SSH_ASKPASS`, `SSH_AGENT_PID`, `SSH_CONNECTION`, or `WINDOWID` either. Those names and several baseline names are in tmux's default `update-environment`. A creating or attaching client that lacks such a name makes tmux mark it removed in that session's environment, so the `t` shell and every later window in the session would lose it.
- Use checks run in `SessionLifecycle` through `HostProbe`, only in the use case that needs them. `create_session` step 1 (section 5) requires an agent, a `command` that resolves, a writable worktree root, and a `{prompt}` in `prompt_args` for a non-empty prompt. A worktree root that does not exist yet passes when its nearest existing ancestor is writable, since `git worktree add` creates the missing directories. `restart` requires the session's agent to exist in config and its `command` to resolve. Delete, rename, attach, `t`, and the `repo` commands run none, so a removed agent or an unmounted root never blocks cleanup. A failed use check refuses only that action, with exit 1 from the CLI or a status-bar message in the TUI.
- A config that fails to parse or fails a load check is handled the same way, and every message names the key or the parse error. A TUI that starts on such a config uses the defaults, shows the error in the status bar, and stays read-only until `r` loads one that passes. Read-only means `observe` runs with `persist` false, and `n`, `d`, `R`, and `s` change nothing and show the error in the status bar, while `Enter`, `t`, `r`, `?`, and `q` still work. A TUI that started on a valid config keeps it when `r` reads a file that fails, and shows the error. Every other command except `doctor` and `__exec-agent` prints the error to stderr and exits 1 before it observes tmux or loads the registry, because under the default prefixes and `worktree_root`, a live managed session with no registry entry would be left out or shown as `Unmanaged`. `doctor` reports each failure as its own finding, skips the checks that need config values, runs the rest, and exits 1.
- Registry at `$XDG_STATE_HOME/ringleader/sessions.json` with a schema version field. Writes are atomic: write a temp file in the same directory, `sync_all` it, rename it over `sessions.json`, then `sync_all` the directory. `save` returns an error only while `sessions.json` still holds the old content. A failed directory `sync_all` after the rename is logged as a warning. Schema policy: `JsonSessionRegistry` parses only the `version` field first and compares it before parsing the entries, so a newer file is never classified as corrupt. A file that fails that version-only parse is corrupt. A newer file is never moved aside and never written. The TUI prints `sessions.json has schema version <n>, but this Ringleader reads up to <m>. Upgrade Ringleader.` to stderr and exits 1 before the terminal guard starts, and every CLI command that loads the registry exits 1 with the same message. A corrupt file is moved aside as `sessions.json.corrupt-<timestamp>` only by a lock holder, which then continues with an empty registry plus a status-bar warning. `list` and `doctor` report a corrupt registry on stderr, exit 1, and change nothing. No migration machinery in v1, since there is no older schema yet.
- The registry is an index, not the source of truth. tmux user options are the source of truth for a live session:
  - `@ringleader_meta` holds one compact JSON object with repo name, repo path, branch, base commit, worktree path, and agent.
  - `create_session` writes it, and `rename_session` updates it in the same invocation as the tmux rename.
- `observe_all` makes one call: `list-panes -a -F` with a fixed label, `#{session_name}`, `#{socket_path}`, `#{session_created}`, `#{window_active_clients}`, `#{pane_id}`, `#{@ringleader_agent}`, `#{pane_dead}`, `#{window_activity}`, and `#{@ringleader_meta}`, tab-separated, with `-u` so the tabs survive any locale. Session user options expand on every pane row; this was verified on tmux 3.6a and 3.7b. A pane user option expands only on its own pane's row. `observe_all` keeps the row of the tagged agent pane for each session. A session with no tagged pane keeps one row for its metadata and is observed as described in section 4. `window_activity` is epoch seconds with 1-second granularity. `pane_last_output_time` is unavailable on tmux 3.6a; `pane_activity` is not a format variable.
- Startup reconciliation merges registry entries with live tmux sessions. An entry pairs with the live session that carries its recorded tmux session name, whatever the current `tmux_prefix`. Any other live session counts only when its name starts with the current `tmux_prefix`, or with the recorded `tmux_prefix` of a registry entry whose worktree path its metadata claims. When the live tmux session name starts with the entry's recorded `tmux_prefix`, a take-over strips that prefix to get the entry's new name. Otherwise it strips the current `tmux_prefix`. Reconciliation follows these rules:
  - live session, valid metadata, no registry entry: adopt into the registry. The adopted name is the tmux session name with `tmux_prefix` stripped, `created_at` is `#{session_created}`, and the socket path is the observed `#{socket_path}`.
  - metadata is valid only if it parses, `repo_path` and `worktree_path` are absolute, `branch` starts with `branch_prefix`, and `worktree_path` passes the containment check of `delete_session` step 3 against `worktree_root`, which a missing worktree directory still passes. For a session paired with or claiming a registry entry, both checks use that entry's recorded `branch_prefix` and `worktree_root`, and for any other session the current config. Anything else is missing or malformed.
  - each registry entry records the canonical `worktree_root`, the `branch_prefix`, and the `tmux_prefix` in force when it was created or adopted, beside its tmux session name and socket path. A re-keyed entry keeps them. `@ringleader_meta` never carries them, since any process on the server, including the agent, can rewrite it. `delete_session` step 3 checks an entry against its recorded values too, restart recreates a `Stopped` entry under its recorded tmux session name, and rename builds the new names from the recorded prefixes, so editing these config keys never makes an existing session unmanageable. `doctor` names every entry whose recorded values differ from the current config. While a row whose tmux session name lacks the current `tmux_prefix` is selected, the status bar says that Ctrl-Q does not return from that session.
  - a live session paired with an entry by name is that entry's session only when its valid metadata names the entry's worktree path and its observed `#{socket_path}` equals the entry's recorded socket path. Otherwise the pair shows as one `Unmanaged` row, and the entry is kept unchanged. A restore plugin such as tmux-resurrect causes this after a reboot, since it recreates sessions by name without their user options. Restart, rename, and delete refuse the row with a conflict that names the tmux session, its socket, and the mismatch, and says `Inspect it, then end it with tmux -S <socket> kill-session -t '=<tmux name>:' to restart or delete this session.` The status bar shows the same text while the row is selected. Ringleader never kills or adopts that session itself, and once it is gone the entry is `Stopped` and restartable in place.
  - a live session whose valid metadata claims the worktree path of exactly one registry entry under a different name takes over that entry, but only when its stripped name is a valid slug that no other entry uses, its own name is no other entry's recorded tmux session name, no live session carries that entry's own tmux session name, and no other live session claims the same worktree path. Otherwise the claiming session is `Unmanaged`. Every reconcile, persisting or not, re-keys a taken-over entry to the live name and updates it from the metadata, including the live tmux session name and the observed socket path, so `list` and every use case see the renamed session. A persisting reconcile writes the result, and the mutating session commands `new`, `delete`, `rename`, and `restart` reconcile with `persist` true under the write lock before they act, so the repair is written without a TUI. Reconciliation updates an entry from metadata only in this take-over. This take-over repairs a rename whose registry write failed after the tmux rename. An entry that no live session takes over stays `Stopped`, and the last rule below refuses restart, rename, and delete while a live session claims its worktree path.
  - otherwise a live session is adopted only when its stripped name is a valid slug that no registry entry uses, and no other registry entry claims its worktree path or the same branch in the same repository, compared by canonical repo path. A branch name alone never conflicts, since two repositories can each hold a branch with that name. A registered live session is checked against the other entries only, never against its own. Creation's availability rules do not apply, since an adoptable session's own name, worktree, and branch always exist.
  - live session with missing or malformed metadata, or one that fails these checks: state `Unmanaged`, attachable only, never edited, restarted, or deleted; warned about in the status bar
  - registry entry with no live session: keep, shown as `Stopped`, restartable in place
  - each registry entry records its server's socket path. A session observed as `Stopped` may still be live on another tmux server, such as a `-L` server, another `TMUX_TMPDIR`, or the other side of inside versus outside tmux. Before restart, rename, or delete acts on a `Stopped` session, it runs `has_session_on` against the recorded socket with the entry's tmux session name and worktree path. A session there with that name, or with `@ringleader_meta` naming that worktree path, refuses the action with a conflict that names the socket. It also refuses when any live session on the current server, with or without `tmux_prefix`, carries valid metadata that claims the entry's worktree path, such as a managed session the user renamed out of the prefix with tmux. `observe_all` already lists every session.
- `observe_all` treats a missing or empty tmux server as zero sessions, not an adapter error. tmux reports that three ways: `no server running on <path>` for a stale socket file, `error connecting to <path> (No such file or directory)` when the socket file is absent, which is the normal state after a reboot, and `no current target` from `list-panes -a` on a live server with no sessions (`exit-empty off`). Any other failure, including `Permission denied` and `server exited unexpectedly`, is an adapter error. On the zero-session path every registry session is simply `Stopped`.
- Locking with `std::fs::File::try_lock` (stable since Rust 1.89) on `$XDG_STATE_HOME/ringleader/lock`. Two locks on the same file conflict even inside one process, so each process takes the lock exactly once, at its entry point:
  - `main` takes an exclusive lifetime lock before starting the TUI. A second TUI exits with a clear message naming the lock path. The TUI persists under this lock and never takes the write lock.
  - `Cli` takes the write lock for mutating commands (section 7) before loading the registry or config, and holds it until the command exits. If the TUI holds it, the command exits 3 with "another instance is running".
  - Read-only commands such as `list` and `doctor` do not lock and do not write the registry.
  - `SessionService` receives no `Lock`.
- The registry write path is single-writer: the TUI lifetime lock is held while it persists, and CLI mutations persist under the write lock. `list` never persists, eliminating the race between a lock-free read and a writer.

## 9. Logging and error handling

- `log` + `env_logger`, default level info, file at `$XDG_STATE_HOME/ringleader/app.log`, `--log-level` flag. Every command except `__exec-agent` creates the state directory with `create_dir_all` before it opens the log or the lock, opens `app.log` with `OpenOptions::new().create(true).append(true)`, and passes that handle to `env_logger` as `Target::Pipe`. Only the TUI after taking its lifetime lock, or a mutating command after taking the write lock, truncates the file when it exceeds 5 MB, in place with `set_len(0)` on that handle, never by replacing the file. Another process can hold the log open during a truncation, and only an append-mode writer then continues at the new end instead of padding the file with NUL bytes up to its old offset. No rotation machinery in v1. Logging never stops a command. When a read-only command cannot create the directory (section 8), or the file cannot be opened, logging is off for that run and never falls back to `env_logger`'s default stderr target, which is the TUI's own terminal. The TUI then shows `logging disabled: <path>: <error>` once in the status bar, a CLI command prints it once to stderr, and `doctor` still runs its state directory check.
- Adapter errors are wrapped with `thiserror` and surfaced in the status bar. The UI never panics on adapter failure. tmux and git adapter errors carry the subcommand name, exit status, and stderr, never the argument vector.
- The panic hook restores the terminal, including bracketed paste, writes the panic to the log, and then calls the default hook so the message reaches stderr. For a panic on a helper thread it only writes the log, since that panic does not end the TUI. `PendingRepos` reports a scan worker that ended without a result as a failed scan, which the picker shows like an unreadable scope root. The hook never releases the lock, so a second TUI cannot start while unwinding still restores the binding. `TerminalGuard` and the hook share one record of whether the terminal is in TUI mode, which suspend and resume update, and a restore outside TUI mode writes nothing. A second `LeaveAlternateScreen` would make tmux move the cursor back to the position saved on entry, where the shell prompt would overwrite the panic message. Terminal state, the return binding, and the lock live in RAII guards so normal exit always restores them. The binding guard runs before the terminal guard and ignores terminal errors. The exit notice from section 6 drops after both. Guard drops ignore every error and never panic, since a panic during unwinding aborts the process. No profile sets `panic = "abort"`, because the binding guard restores on panic only through unwinding.
- SIGHUP, SIGINT, SIGTERM, and SIGQUIT are registered as flags with `signal-hook`. The event loop checks them every tick and returns normally, so the guards run. SIGHUP is the usual way the TUI ends when its tmux pane or terminal window closes. Mutating CLI commands register the same flags for their whole run, so neither a closed terminal nor Ctrl-C stops one between two steps of a use case. Without the SIGINT flag, Ctrl-C would kill Ringleader while a `git worktree add` in its own session finished alone, leaving a worktree and a branch with no tmux session or registry entry. A command whose SIGINT flag was raised finishes its use case, including any rollback after a failed step, prints its normal result, writes to stderr that the interrupt waited for the command to finish, and reports the interrupt to `main` with its exit code. `main` then ends with `signal_hook::low_level::emulate_default_handler(SIGINT)`, so a calling shell script stops as it would for any Ctrl-C. `Cli` never makes that call, because it would end the test process in a `Cli` test. `Cli` checks every flag just before it calls the use case that acts. A flag raised by then ends the command without running it, and `main` ends with `emulate_default_handler` for that signal, as for `new` while it waits for `discover_repos` (section 5). A second Ctrl-C only raises the flag again, since ending the process then would split the use case, and the child deadlines below bound the wait.
- Every command writes to stdout and stderr with `writeln!`, never `println!` or `eprintln!`, which panic once the reader or the terminal is gone. That covers `list`, `doctor`, `repo list`, the mutating commands, and the saved binding the TUI prints on exit. A write error never stops a use case and never changes the exit code, and a read-only command stops printing at the first `BrokenPipe`, so `ringleader list | head -1` exits 0.
- Ringleader enables crossterm's `use-dev-tty` feature, whose event source returns when the poll timeout expires. The default source retries a hung-up tty with no deadline, so the TUI would spin at full CPU, never check the signal flags, and keep the lifetime lock. When polling input or drawing a frame fails, the event loop checks the signal flags before it returns the error, and a raised flag makes it return normally.
- Every git and tmux child that does not take over the terminal runs through `BoundedCommand`, which `TmuxCommand`, `GitWorkspace`, and `DirectoryRepoScanner` take through their constructors. It starts the child in a new session with no controlling terminal through a `CommandExt::pre_exec` closure that calls `libc::setsid`. The child's stdin is `Stdio::null()`, or a pipe that is closed once the call's input is written, such as the line `source-file -` reads. git children also get `GIT_TERMINAL_PROMPT=0`. The `setsid` closure replaces `CommandExt::process_group(0)`, and the two are never combined, because `setsid` fails with `EPERM` in a process group leader. In a new session, a child that opens `/dev/tty`, such as a post-checkout hook, an ssh passphrase prompt, or a Git LFS credential prompt, fails at once with `No such device or address` instead of stopping on SIGTTIN, and the nonzero git exit fails the step like any other git failure. A closed terminal signals only its own session, so these children never receive its SIGHUP. git can never prompt in the terminal, so credentials that git needs during checkout must come from a credential helper, an askpass program, or `ssh-agent`, and the README says so.
- `BoundedCommand` reads stdout and stderr on two threads and polls `try_wait` every 10 ms until the child exits or its deadline passes. After the child exits, it waits at most 1 more second for the readers and then leaves them detached, because a process the child started can keep the pipes open. Deadlines: 2 seconds for a tmux call that changes nothing, such as `list-panes` or `capture-pane`, 10 seconds for any other tmux call, 5 seconds for `diff_stat`, 60 seconds for other git reads, and 300 seconds for a git command that changes a repository, since hooks and filters run inside it. At the deadline it sends SIGTERM to the child's process group with `libc::killpg`, and SIGKILL to the group if the child has not exited 2 seconds later. SIGTERM comes first because git then removes an unfinished worktree, which a SIGKILL during checkout leaves locked (`create_session` step 4). The call returns a timeout error that names the subcommand and the deadline. When the child is still alive 1 second after the SIGKILL, the call returns anyway, because a child blocked on a FUSE daemon that never answers ignores SIGKILL (section 16). A detached thread then waits on that child and reaps it if it ever exits. `BoundedCommand::spawn` holds the `setsid` closure and `BoundedCommand::signal_group` holds the `killpg` call, and these are its only `unsafe` blocks. Tests inject short deadlines. The outside-tmux `attach-session` child and the ephemeral shell take over the terminal and have no deadline.
- Port errors carry a timeout variant, so use cases and the TUI can tell a timed-out call from a failed one. A use case treats a timed-out git call as a failure of the step that ran it. A timed-out tmux call has an unknown outcome, because a stopped server still runs a delivered command when it resumes, and a busy server drops the rest of the sequence once its client is killed. So a tmux timeout alone never rolls back git work. `create_session` runs its `kill-session` cleanup and removes the worktree and branch only when that call completes, and keeps both when it also times out. `rename_session` keeps the renamed branch and persists nothing, and `delete_session` stops and keeps the worktree, the branch, and the registry entry. The error names what remains and points to `doctor`. A timed-out `switch-client` is never retried, and a timed-out `ReturnBinding` call keeps `bindings.json`, so the next startup repair retries the restore. A timed-out `install` cancels its attach or shell open with a status-bar error, because the outside-tmux `attach-session` child has no deadline and would wait on that server with the TUI suspended. After a tmux call times out, the TUI makes no observe, preview, or bell call to that server for 30 seconds or until `r`. After a `diff_stat` call times out, the TUI shows no diff for that row and does not queue the row again until `r`.

## 11. Tooling and CI

- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, all through `nix develop` so local and CI use the same rustc 1.95.
- In a binary crate, anything `main` cannot reach yet is dead code, and most of milestones 2 to 28 build ahead of their wiring. Until then, `main.rs` carries `#![allow(dead_code, unused_imports)]`, unconditionally. A `cfg_attr(not(test), ...)` form does not work, because `--all-targets` also compiles the binary under `cfg(test)`, where unused re-exports and unwired port traits would fail `-D warnings`. Milestone 29 removes it, and `cargo clippy --all-targets -- -D warnings` must pass without it. `--all-targets` also checks the non-test binary, where anything only tests use stays dead after wiring. Prefer constructors that production and tests share, such as a `ProcessEnvironment` constructor from name and value pairs plus an optional terminal name, which `capture` calls and tests call with fixture values. A constructor, accessor, or helper that only tests call carries `#[cfg(test)]` from the milestone that adds it, and a field that only such code reads does not exist.
- `.github/workflows/ci.yml` triggers on `push` and `pull_request` and runs on `ubuntu-latest`: `actions/checkout`, the DeterminateSystems Nix installer, then `nix develop -c cargo fmt --check`, `nix develop -c cargo clippy --all-targets -- -D warnings`, `nix develop -c cargo test`, `nix build .#`, and `nix flake check`. No separate toolchain action. The dev shell is the single source of truth.
- The GitHub repository exists, so the workflow runs on GitHub as soon as it is pushed.

## 12. Flake for this repo

- Input `nixpkgs` pinned at `nixos-26.05` for stability.
- The flake defines its outputs for `x86_64-linux` and `aarch64-linux` only, the platforms section 2 supports.
- `packages.default = rustPlatform.buildRustPackage` with `cargoLock.lockFile`, `meta.license = lib.licenses.mit`, and `makeWrapper` in `nativeBuildInputs`, wrapped in `postInstall` with `wrapProgram $out/bin/ringleader --set-default RINGLEADER_TMUX ${tmux}/bin/tmux --set-default RINGLEADER_GIT ${git}/bin/git`, so `nix run` works standalone. The wrapper leaves `PATH` unchanged. Every agent, `t` shell, and window on a server that Ringleader starts inherits Ringleader's `PATH`, so a wrapper that prepended the pinned tools would shadow the user's own `git` and its credential helpers in all of them.
- `doCheck = true` with `nativeCheckInputs = [ git tmux ]`, so `nix build` runs the test suite, including the tmux tests on per-test sockets. The sandbox has no usable `HOME` and no git identity, which the hermetic git environment in section 10 provides.
- `devShells.default`: rustc, cargo, clippy, rustfmt, tmux, git, nixfmt, and util-linux, which provides `script` for milestone 9.
- `formatter = nixfmt-tree`, `checks` build the package. Commit `flake.lock`.

## 16. Risks to verify early

- Worktree removal never deletes recursively. `git worktree remove --force` after the guards handles submodule worktrees. It deletes the worktree's submodule repositories and nested repositories with it, so the guards count unpushed submodule commits and name each nested repository. Anything git refuses up front (a main worktree, a path that is not a worktree, a locked worktree) is reported and left alone. A removal that fails partway leaves a partly deleted, unregistered directory, which `delete_session` step 6 reports.
- Ctrl-Q root binding conflicts with the user's tmux config. Restore correctness on crash is handled by the saved-binding record keyed by server plus startup repair; `key-table` is rejected and documented as such.
- tmux behavior follows the server's version, which can differ from the pinned client. A 3.7 server prints nothing for `list-keys -T root -1 C-q`, bound or not, and nothing for `list-keys -T root` when the root table holds one binding, so the saved binding comes from the full `list-keys` listing.
- The inside-tmux attach path uses `switch-client`, never `attach-session` from a child process. A terminal started from a pane inherits `$TMUX` and `$TMUX_PANE`, so the inside-tmux flag also requires the pane's foreground to hold this process or an ancestor (section 2).
- Bare tmux targets prefix-match other sessions. Every target is `=<session>:`, a `window_id`, a `pane_id`, or, for rollback only, a `session_id`.
- The return binding is installed before each attach rather than at startup, because a server with no sessions exits.
- `window_activity` has 1-second granularity, so a pane that prints continuously can read 1 second old, and `activity_idle_seconds` must be at least 2.
- Detached session sizing (`-x/-y`) holds only until the first attach, after which `window-size latest` keeps the last client's size. The preview crops whatever size it captures.
- Terminal raw mode and alternate screen restore around `tmux attach`, including the full redraw on resume, moved early as the milestone 9 vertical slice.
- Resize events must force a redraw so tiers and the too-small guard recalculate instantly.
- Unborn-HEAD repos use `git worktree add --orphan` instead of erroring on the base-branch ladder; this needs git 2.42.
- Initial prompt argv must stay one element per template entry; a prompt with quotes, shell metacharacters, or a trailing `;` must reach the agent intact, which the handoff file guarantees. Both Claude Code and opencode were verified to accept it, but agents change their flags; `doctor` reports a non-empty `prompt_args` that lacks `{prompt}` (section 7). The handoff file protects the argv, not the agent's option parser, which is why opencode's template uses `--prompt={prompt}`.
- The launcher's cleared environment must keep the baseline, or agents fail to resolve, lose their auth, and render without `TERM`.
- Branch rename rollback ordering in `rename_session`.
- Dirty worktree removal, unmerged commits, and branch deletion safety, including the explicit confirmation for a `Working` session and re-checking the guards at execution time. `kill-session` returns before the pane processes exit, and `nohup` and `setsid` children survive it, so delete stops the session's processes and the processes running in the worktree, then re-reads the branch tip and worktree HEAD before step 6. A `setsid` child whose working directory is outside the worktree keeps running. The branch is deleted only at the tip the guards counted.
- Activity heuristic false positives if an agent paints an idle animation, tunable via `activity_idle_seconds`. The user's own typing also counts as activity, so a session the user is typing into can read as `Working`. The bell skips a session whose agent window a client shows for that reason. Output in a pane the user splits off the agent window also counts, since `window_activity` covers the whole window.
- `ansi-to-tui` parsing of capture output. Always keep the plain text fallback.
- Preview and diff load: only the selected session is captured, which is one cheap tmux call even on the fast preview timer. Diffs are computed for visible rows only, on the slower `diff_refresh_ms` timer. Git work per tick is bounded. If round-robin refresh still stalls input on large repos, move git work to one `std::thread` worker over a channel, still without an async runtime.
- A closed terminal or tmux pane must end the TUI within a tick and free the lifetime lock. crossterm's default event source spins forever after a hangup, so the TUI depends on the `use-dev-tty` feature (section 9), and milestone 9 checks it by hand.
- A stopped tmux server or a hung git hook must not freeze the TUI, its startup, or its exit past the child deadlines, and a child that reads the terminal must not stop. Every git and tmux child that does not take over the terminal runs in its own session with a deadline (section 9).
- Lock contention between a running TUI and CLI mutations, make the message actionable, exit 3.
- User option expansion in `list-panes -F` was verified on tmux 3.6a and 3.7b, so `observe_all` reads `@ringleader_meta` from its single call and has no per-session fallback. An empty `#{@ringleader_meta}` means the session has no metadata. Never check session existence with `show-options -qv`, which exits 0 with empty output for a missing session.
- Adoption when the worktree was deleted manually: adopt the session, surface the missing worktree in `doctor` and the status bar.
- Global `destroy-unattached` in the user's tmux config is why creation and configuration happen in a single tmux invocation. A server with `exit-unattached` on cannot keep detached sessions at all, so creation detects it and refuses.
- User `after-` hooks print into Ringleader's own invocations and can make tmux exit nonzero after every Ringleader command ran, so output is read by label and success comes from the `ringleader-done` line (section 2).
- tmux server environment drift: `-e` does not strip the inherited server environment, so the `__exec-agent` launcher owns the real allowlist, and values travel only in the handoff file. The reverse leak, a new server copying its first client's environment, is handled by removing the configured agent `env` names from every tmux child and by passing `-N` to every invocation that does not run `new-session`.
- tmux replaces tabs and non-ASCII bytes in its output with `_` when the client locale is not UTF-8. `-u` on every invocation prevents it, and the Nix build sandbox, which has no `LANG`, exercises that path.
- `git rev-list --all` includes the HEAD of every worktree, which would hide every session's commits from the unmerged-commit guard.
- Porcelain `git diff` rewrites a worktree's index under `index.lock` even with `GIT_OPTIONAL_LOCKS=0`, and `git status` does without it. Both would collide with the agent's own git commands, so DiffStat uses `diff-index` and every read runs with `GIT_OPTIONAL_LOCKS=0`.
- Registry `list` race: `list` reconciles in memory and never persists, single-writer elsewhere.
- Repo scan scope: a launch from `$HOME` or `/` can make a large walk, list tool clones, or reach a stale network mount. Mitigated by the depth cap, pruning, skipping hidden directories below the scope root, the breadth-first order that finds shallow repos before the cap stops the walk, the skipped system directories and network and FUSE mount points, the 5,000-directory cap with a notice, the scan worker, and the empty state. A thread blocked on a FUSE daemon that read its request but never answers ignores even SIGKILL, so a scope or configured repo on such a mount can keep the process alive after `q`. The lifetime lock is already released then, since its guard drops when `main` returns.
- Two repos can share a name, from scanned basenames or from a scanned repo and an explicit entry at another path. Repos are keyed by canonical path everywhere. A `--repo` name that matches more than one exits 1. Worktree paths never collide, because session slugs are unique across repos.
- Agent command resolution under Nix: the wrapper leaves `PATH` unchanged, so agents and shells resolve the user's own `git`, `tmux`, and agent commands, and absolute commands in config also work. Ringleader itself runs the pinned `tmux` and `git` by absolute path.

## 17. Out of scope for v1

- Mouse support.
- Configurable keybindings.
- `doctor --fix` auto-repair.
- Registry schema migration machinery; only refuse-newer and corrupt-file backup.
- Log rotation; truncate on startup instead.
- The per-session `key-table` Ctrl-Q alternative; rejected after testing on 3.6a.
- A recursive-delete fallback for worktrees git refuses to remove or removes only in part.
- Agent-specific activity detectors beyond tmux pane activity.
- Session output logging or transcript search, agent tooling owns that.
- macOS and other non-Linux platforms.
